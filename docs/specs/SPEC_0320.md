# SPEC_0320: Cabinet v0.32.0, share and showcase view (P9)

Status: **approved by the owner on 23 September 2026** (the four
questions answered at the end). Planned the day after v0.31.0 as the next
item: P9 ahead of P8 A2 (single sign-on), which moves to v0.33.0. Built on
`p9-share` (PR 25), stage by stage.

## Why

Since v0.30.0 every page and route needs a session or a token. The owner
wants to show the collection, a set, or a checklist to someone without
handing them a login: a read-only page behind an unguessable link that can
be revoked, and a switch that turns the whole feature off. The roadmap set
the rules on 20 September 2026 (Phase 7, P9): the feature is **off by
default**, while it is off no link can be made and the public routes
answer "not found" as if they didn't exist, links made earlier stop
working without being deleted (so switching back on restores them),
Settings lists every live link with when it was last opened, and a share
**never** shows costs, gains, storage locations, or documents (the
permission table in `docs/security.md`, "Share link" column); the
estimated value alone can be switched on per link, off by default (the
owner's decision of 23 September 2026).

## What the research found

- **Other tools.** Numista and Colnect show a member's collection to
  anyone, always public. Koillection has per-collection visibility
  (private, internal, public) with a public URL. Google Photos and Drive
  share by an unguessable link that can be turned off, and both let the
  owner copy the link again later. Nothing surveyed has a per-link choice
  of *what* is shown; Cabinet's "never costs, never storage" rule plus a
  few toggles is more than any of them offer.
- **Cabinet today.** The gate (`app/auth/gate.py`) lets anonymous callers
  reach exactly four `(method, path)` pairs, all exact matches, and every
  route declares a class from `public`, `read`, `write`, `admin`. Photos
  are served by nginx after `auth_request` to `GET /api/auth/photo`, which
  answers 204 for a session or a read or write token and nothing else. The
  frontend's `Gate` (`App.tsx`) runs the boot check (`GET /api/auth/state`,
  `GET /api/auth/me`) before any route renders, so a public page has to sit
  **outside** it. Sets (`sets`, id and name) and checklists (`checklists`,
  with slots matched to owned items on read) are the two groupings a link
  can point at; the collection is the third target. Settings are one
  `app_settings` table; the master switch is one more key. Backups carry
  `public`, never `cabinet_auth`, so a share-links table in `public` rides
  along in every archive and restore, which is right: links are collection
  data, not credentials.
- **The threat that matters** is not guessing a link (a 256-bit token is
  not guessable) but a page that shows more than the owner meant: a field
  forgotten in a serializer, a photo of an item outside the share, a
  document, a search engine indexing the page. So the share serializer is
  an **allowlist** with a test that pins its keys, photos are served only
  through the share's own route after checking the photo belongs to a
  shared item, documents have no share route at all, and every share
  response and page carries `X-Robots-Tag: noindex`.

Options weighed for the link itself: **A**, the token stored hashed and
shown once, with a "regenerate" that replaces a lost link (**chosen**: the
same standard as API tokens, and a regenerated link costs the owner one
message to the person it was sent to); B, the token stored in clear so
Settings can show the link again (what Drive does; a readable copy in
the database, though backups are encrypted now); C, a signed link with an
expiry baked in (no revocation without a key change; rejected).

## Scope

**In scope**

1. **The switch.** `share_enabled` in `app_settings` (default `false`),
   set through `PUT /api/settings` (admin, password again, as every
   settings change is). While off: every `/api/share/...` route answers
   `404 {"detail": "Not found"}`, the same body for a wrong token, an
   unknown token, and a revoked link, so nothing tells a caller whether
   sharing exists; creating or regenerating a link answers `409` with a
   message that says to switch sharing on first; existing rows stay.
2. **Share links** (`share_links`, schema `public`, migration `0022`):
   `id` (uuid), `token_hash` (SHA-256 of the token; the token itself is
   never stored), `kind` (`collection` | `set` | `checklist`),
   `target_id` (nullable integer; the set's or checklist's id), `name`
   (what the page is titled, `String(100)`), `show_photos`,
   `show_grades` (grade, designations, cert service and number),
   `show_tags`, `show_notes`, `show_values` (all booleans; defaults on,
   on, on, off, off), `created_at`, `created_by` (the admin's username as
   text; no foreign key into `cabinet_auth`), `last_opened_at`, `opens` (integer), and no
   `revoked_at`: revoking a link deletes its row. A link whose target set
   or checklist is deleted is deleted with it (a foreign key with cascade
   on `sets` and `checklists`; the collection kind has no target).
3. **The token.** 32 random bytes, base64url, 43 characters, `share_`
   prefix (`share_[A-Za-z0-9_-]{43}`), shown once in the creation and
   regeneration answers as a full URL (`{PUBLIC_ORIGINS[0]}/s/{token}`).
   The public routes read it from the path only, never a query string or
   a header, so it never lands in a referrer of an outbound link (the
   share page sets `Referrer-Policy: no-referrer` too) and the gate's
   refusal of `%` in a path still covers it.
4. **Public routes** (class `share`, a new class in `permissions.py`:
   anonymous allowed, no session or token needed, and a session or token
   is ignored rather than trusted, so a signed-in admin previewing a link
   sees exactly what a stranger sees):
   - `GET /api/share/{token}`: the share's manifest: `kind`, `name`, the
     options, `item_count`, and for a checklist its completion figures.
   - `GET /api/share/{token}/items?offset=&limit=` (limit at most 100):
     the items the link covers (the collection's owned pieces, a set's
     pieces, a checklist's matched pieces), each through the **share item
     view**, an allowlist: `id`, `type`, `country`, `denomination`,
     `year_label`, `mint_mark`, `series`, `variety`, `composition`,
     `weight_g`, `fineness`, `diameter_mm`, `width_mm`, `height_mm`,
     `shape`, `issuer`, `quantity`, `photos` (id, angle, has thumbnail;
     only with `show_photos`), `grade_label`, `grade_details`,
     `designations`, `cac_sticker`, `cert_service`, `cert_number` (only
     with `show_grades`), `tags` (only with `show_tags`), `notes` (only
     with `show_notes`), and `value` (only with `show_values`: the piece's
     shown estimate, resolved the way the list resolves it
     (`pricing.resolve_display_value`, the `value_strategy` setting) and
     converted to the display currency, as `{amount, currency}`, or
     `null` when it has none; the owner's decision, 23 September 2026).
     **Never**: any cost, fee, gain, acquisition or sale field, the
     estimate's source or history, storage location, documents, serial
     numbers, custom fields, population, wish-list fields, spot at
     purchase, import origin, timestamps, the edit history. A test pins
     the allowlist: the view's keys for an item with every field filled
     equal the list above, exactly, with and without each toggle.
   - `GET /api/share/{token}/items/{id}`: one item through the same view
     (404 unless it is in the share).
   - `GET /api/share/{token}/checklist`: for a checklist link, the
     **filled** slots only (position, label, year, mint mark, the piece's
     id), so the page shows what is there and never a want list (the
     owner's decision, 23 September 2026); the manifest carries the
     completion figures (filled of total); `404` for the other kinds.
   - `GET /api/share/{token}/photos/{photo_id}/{variant}` (`thumb` or
     `full`): the file streamed by the API, `404` unless `show_photos` and
     the photo belongs to an item in the share, sent with `Cache-Control:
     private, max-age=3600` and the security headers documents already
     get (`nosniff`, a `default-src 'none'` CSP). Photos never go through
     nginx's `/photos/` for a share: that check stays "session or token".
   - Every share response carries `X-Robots-Tag: noindex, nofollow` and
     `Cache-Control: no-store` (the JSON) and counts an open: the manifest
     route updates `last_opened_at` and `opens` (once per request, no
     dedup: a count of page loads is what the owner wants to see).
   - Unknown or revoked tokens are throttled per address like failed
     sign-ins (`throttle` bucket `share:<address>`, the same delay curve,
     429 with `Retry-After` past the limit), so a scanner is slowed and
     the audit log stays quiet; nothing about a token is ever logged.
5. **Admin routes** (`admin`; the password again for the ones that mint
   or kill a link, the same as API tokens):
   - `GET /api/share-links`: every link with its kind, target name,
     options, `created_at`, `last_opened_at`, `opens`; never the token.
   - `POST /api/share-links` (fresh): create; answers the row plus `url`
     once; `409` while sharing is off; at most 20 live links.
   - `PATCH /api/share-links/{id}` (admin): rename or change the options.
   - `POST /api/share-links/{id}/regenerate` (fresh): a new token, the old
     one dead at once; answers the new `url` once.
   - `DELETE /api/share-links/{id}` (fresh): revoke, for good.
   - Audited (`share_link_created`, `share_link_regenerated`,
     `share_link_revoked`, `sharing_switched`, with the link's id and name,
     never the token) and alerted through the webhook like token events
     (`alerts.event`), so a link made from a stolen session is noticed.
6. **The share page**, `/s/{token}`, rendered outside the auth `Gate`
   (`App.tsx` routes `/s/*` before the boot check; it never calls
   `/api/auth/state`): the brand header without navigation, the share's
   name, a search box over what is shown, a grid of pieces (thumbnail,
   label, grade when shown), a piece's own page at `/s/{token}/items/{id}`
   (photos with the existing lightbox, the allowed facts in the item
   page's grouped style), a checklist's slots with what is filled, the
   theme toggle, and a footer "Shared from Cabinet" linking nowhere. A
   404 from the API shows one page: "This link isn't active." The page
   sets `<meta name="robots" content="noindex">` and nginx adds
   `X-Robots-Tag` on `/s/` and a `robots.txt` that disallows `/s/`.
7. **Settings → Sharing** (a seventh section): the switch, with the
   sentence that makes the consequence plain ("Anyone with a link can see
   what it shares, without signing in. Costs, values, storage, and
   documents are never shown."); the links table (name, kind and target,
   opens, last opened, created, Rename, Options, Regenerate, Revoke); a
   create form (kind, target from the existing sets or checklists, name,
   the five toggles, values last and off, with the sentence "Shows each
   piece's estimated value; costs and gains are never shown"); the new URL
   shown once with a Copy button, the way a new API token is. The whole section reads as off while the switch is
   off, with the links listed but marked inactive.
8. **Metrics**: `cabinet_share_links` (live links) and
   `cabinet_share_opens_total`; a `share` line in `status`.

**Out of scope:** per-item sharing (a set of one does it), a public
collection without a link (the roadmap's rule: always a link, always
revocable), showing costs or gains under any toggle (only the estimated
value can be, off by default), comments or reactions from viewers,
expiry dates on links (revoke does it), embedding the page elsewhere (the
CSP and `frame-ancestors 'none'` stay), and share links for a viewer or
editor role (those roles don't exist).

## API changes

| Where | Change |
| --- | --- |
| Settings | `share_enabled` (bool, default false) on `GET`/`PUT /api/settings` |
| New public routes | `GET /api/share/{token}`, `.../items`, `.../items/{id}`, `.../checklist`, `.../photos/{photo_id}/{variant}`; class `share` |
| New admin routes | `GET`/`POST /api/share-links`, `PATCH`/`DELETE /api/share-links/{id}`, `POST /api/share-links/{id}/regenerate` |
| `/api/metrics` | `cabinet_share_links`, `cabinet_share_opens_total` |
| Migration | `0022_share_links` |

SPEC_0300's permission appendix gains the rows above (a new class,
`share`, whose rule the gate and `test_gate.py` learn: anonymous allowed
on `GET`/`HEAD` under `/api/share/`, every other method refused, any
credential ignored), and the anonymous matrix gains "every share route
answers 404, not 401, while sharing is off". The `/api/openapi.json`
document stays session-only.

## The owner's answers (23 September 2026)

1. **Order and version.** P9 ships as v0.32.0; single sign-on (P8 A2)
   moves to v0.33.0, and every document says so.
2. **A lost link** is replaced: the token is stored hashed and shown once,
   with Regenerate (the API-token standard).
3. **Values on a share** are a fifth toggle, `show_values`, off by default:
   the estimated value only; costs and gains never. `docs/security.md`'s
   permission table gains that nuance in the share-link column.
4. **A checklist share** shows its filled slots only.

## Build log

- **Stage 1, backend** (23 September 2026): the `share_enabled` setting,
  `share_links` (migration `0022`), `services/share.py`, the public
  `routers/share.py` and admin `routers/share_links.py`, the `share` class
  in `permissions.py` and the `/api/share/` prefix in the gate, the audit
  and alert events, the appendix table in SPEC_0300, the two metrics and a
  `status` line, and `tests/test_share.py`. One change from the text above:
  the single `target_id` became two nullable columns, `set_id` and
  `checklist_id`, since one column can't carry a foreign key to both `sets`
  and `checklists`, and the cascade needs a real key for each. Also
  decided: only a failed link lookup counts against the address (a 404
  inside a resolved share, such as a missing photo file, doesn't, so a
  valid link can't throttle its own viewer); a photo route's `thumb` falls back to the full
  image when a photo has no thumbnail. Found while building it: the
  token is in the path, so uvicorn's access log would have printed it;
  a filter on `uvicorn.access` now writes `/api/share/[token]` instead.
  nginx's access log does the same for `/api/share/` and `/s/` requests,
  which stage 2 has to redact in `proxy/nginx.conf`.
- **Stage 2, the frontend** (23 September 2026): the share page
  (`frontend/src/pages/share/`), Settings → Sharing
  (`pages/settings/Sharing.tsx`), and nginx's `/s/` location, `robots.txt`,
  and the access-log redaction. The share routes are checked for in
  `App.tsx` before `AuthProvider` is even mounted, so a share visitor's
  browser never runs the sign-in boot check at all; every call the share
  page makes is `raw`, so a 404 (an inactive link) is handled by the page
  itself. Found while building it: `try_files`'s fallback to `/index.html`
  is an internal redirect nginx re-matches from scratch, so headers set
  directly in `location /s/` never reached the response (`location /`
  served the fallback instead); the fix is a named location,
  `@share_index`, that owns the fallback and the extra headers (and its
  own `auth_request off`, which a named location doesn't inherit from
  wherever it was reached from). See "Share and showcase view" in the
  implementation notes for the rest.
- **Stage 3, proof and paperwork** (23 September 2026): `frontend/e2e/share.spec.ts`
  (a collection link end to end, in a browser context with no storage
  state at all), a `share` phase in `scripts/ci/stack-smoke.sh` (and its
  own CI step), a `share` mode in `docs/screenshots/capture.cjs`, and the
  version and documentation pass that closes this release out. Found while
  building it: `location /` and `@share_index` had been carrying the same
  Content-Security-Policy string by hand since stage 2, which is exactly
  the kind of drift the spec's allowlist approach was meant to avoid
  elsewhere; both now `include` one `proxy/cabinet-csp.conf`. The owner's
  requirement that sharing be closed by default extends to a deployment's
  own second door: an authenticating reverse proxy in front guards
  everything behind it, so it has to exempt `/s/`, `/api/share/`, and
  `/robots.txt` from its own check or it blocks the very links this
  feature exists to hand out; documented in `docs/deployment.md`, with a
  Traefik + Authentik example.
