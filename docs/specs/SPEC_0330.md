# SPEC_0330: Cabinet v0.33.0, single sign-on (P8 A2)

Status: **proposal, 24 September 2026, waiting for the owner's answers**
(section 1). Planned the day after v0.32.2 shipped, as the last item of
roadmap Phase 7 before the road to v1.0.0. To be built on `p8-auth-a2`,
stage by stage, once approved; a fresh-context security review before the
release, as for A1 and P9.

## Why

Since v0.30.0 the admin signs in with a username and a password, and the
recommended deployment keeps an authenticating reverse proxy in front as a
second door, because Cabinet's own sign-in has no second factor and no way
to reuse the identity the homelab already has. A2 closes that: the same
admin signs in through an OpenID Connect provider, or through the identity
a forward-auth proxy has already checked, and the local password gains a
second factor of its own (passkeys). The password stays, so an outage at
the provider can never lock the owner out, and so the container's
break-glass reset keeps working.

What is settled and not reopened here (the owner's decisions of 20 and 21
September 2026): one admin and one collection; login always on; the
deny-by-default gate with `@permission` classes, enforced by
`tests/test_gate.py` against SPEC_0300's appendix; sessions in
`cabinet_auth` (next revision `a0002`); nginx trusts no forwarded header
and blanks identity headers; the local password stays; more accounts are
not part of A2.

## 1. The owner's questions

Answer these first; everything below is written to the recommended answer
and changes where a different one is chosen.

1. **Where the "password again" comes from on a single sign-on session.**
   Today a fresh action asks for the local password. Recommended: a session
   confirms with the method it signed in by. A password session types the
   password (as today); an OpenID Connect session is sent back to the
   provider with `prompt=login` and `max_age=0` and passes when the new ID
   token's `auth_time` is under two minutes old; a trusted-header session,
   which the proxy can't step up, uses a passkey if one is registered, else
   the password. The password always works on any session. Alternative,
   simpler: the password on every kind of session (one dialog, no new
   flow), at the cost of an SSO-only owner still needing to remember it.
2. **Passkeys as a second factor, or as a sign-in of their own.**
   Recommended: both, in this order. Registering the first passkey turns on
   "password and passkey" for password sign-in (2FA), and a passkey can
   also sign in alone (passwordless, user verification required). An
   OpenID Connect sign-in is **not** asked for a passkey, since the provider
   brings its own second factor (the roadmap's "or the identity provider's
   own"); a switch (`require_passkey_for_sso`, off) asks anyway.
3. **How a trusted-header sign-in starts.** Recommended: one click on the
   sign-in page ("Continue as <name>, signed in at the proxy"), never
   automatic, so signing out of Cabinet means something while the proxy
   session lives on. Alternative: automatic when the proxy asserts an
   identity and no Cabinet session exists (fewer clicks, but sign-out
   bounces straight back in).
4. **Shared-secret header mode: build it, or signed assertions only.**
   Recommended: **signed assertions only** in v0.33.0 (Authentik's
   `X-authentik-jwt`, Pomerium's `X-Pomerium-Jwt-Assertion`, Cloudflare
   Access's `Cf-Access-Jwt-Assertion`, Google IAP's
   `X-Goog-IAP-JWT-Assertion`: each a JWT the gateway signs and Cabinet
   verifies against the gateway's published keys). A shared-secret header
   (`Remote-User` plus a static secret the proxy adds) proves only that the
   request passed through the proxy, and whoever holds the secret is the
   admin: it is a second password on the wire. Authelia and oauth2-proxy
   users would then sign in through **OpenID Connect** instead, which both
   provide. Alternative: add the shared-secret mode as a third path, never
   able to confirm a fresh action.
5. **One linked identity, or one per provider.** Recommended: an
   `identities` table allowing one identity per configured provider plus
   one for the trusted-header mode (Q9 widened this from one per mode),
   since a homelab may run the proxy against one provider and sign in
   through Google or GitHub as well, and drop the two unused `users` columns
   (`external_issuer`, `external_subject`, null everywhere today) in
   `a0002`. Alternative: keep the columns and allow exactly one identity.
6. **Where the provider configuration lives.** Recommended: in
   `cabinet_auth` (a single-row `auth_config` table), not `app_settings`,
   because how the admin signs in is deployment state the way the admin's
   password is: a restore never changes it, an archive never carries the
   client secret, and there is no put-back dance as with share links. The
   client secret is Fernet-encrypted with the same key as the API keys.
   Alternative: `app_settings` keys (carried by backups, put back after a
   restore like share links).
7. **Logout at the provider.** Recommended: local only by default, plus an
   optional "also sign out at the provider" (RP-initiated logout through
   `end_session_endpoint`, if the provider publishes one) as a switch, off.
8. **The mock provider for CI.** Recommended: a ~200-line stdlib Python
   OpenID Connect provider in `scripts/ci/mock_idp.py`, run as one more
   service in a CI-only compose override, auto-approving with a chosen
   subject and able to misbehave on request (wrong nonce, expired token,
   wrong audience, unknown key), so the smoke script and Playwright can test
   the failures too. Alternative: `dexidp/dex` with static passwords (a real
   provider, more faithful, but no way to make it misbehave).
9. **Sign-in buttons for GitHub and the like.** Decided by the owner on
   24 September 2026: **in scope.** GitHub is OAuth 2.0 without an ID
   token, so Cabinet gains a second provider kind, `oauth2_profile`, that
   reads the identity from the provider's profile endpoint after the code
   exchange (section 5a), with GitHub as its one tested preset. Presets
   for Google and Microsoft (plain OpenID Connect, no new code) fill the
   issuer for the owner. Several providers can be configured at once, one
   button each, and the admin can link one identity per provider. Left to
   confirm: whether Discord should join GitHub as a second
   `oauth2_profile` preset (recommended: not now; the kind is generic, a
   preset is a few lines and a live check later).

## 2. What the research found

**Providers.** OpenID Connect is one protocol; every mainstream identity
provider speaks it, and Cabinet gains nothing provider-specific. What
differs is quirks a generic client has to tolerate, and a short list of
services that are not OpenID Connect providers at all (section 3).

**The library.** Three candidates for the OpenID Connect client:

- `authlib`: a full client, but its Starlette integration wants Starlette's
  `SessionMiddleware` (a signed cookie session Cabinet doesn't have) and
  its lower-level `OAuth2Session` hides exactly the steps a review has to
  read (state, nonce, PKCE, token validation).
- `joserfc` (the same author, newer): JWT and JWKS only, well maintained.
- **`PyJWT` (recommended)**: JWT verification with `PyJWKClient` for the
  provider's key set (a two-tier cache, refetched on an unknown `kid`),
  RS256/PS256/ES256/EdDSA through `cryptography`, which is already in the
  lockfile. PyJWT 2.14 is current and Debian-packaged.

The flow itself (discovery, the authorization redirect, the code exchange
over `httpx`, which Cabinet already has) is about 300 lines written by hand
in `app/auth/oidc.py`, so every step is readable in one file, as the gate
and the password check are. The only provider-specific parts are the
preset table's URLs and field names (section 5a); no provider gets code of
its own.

**Passkeys.** `webauthn` (py_webauthn, Duo Labs, latest release June 2026,
Python 3.10 and up) for the server side: registration and authentication
verification, `cryptography` underneath. Frontend:
`@simplewebauthn/browser` (v14, MIT, small, no network use, so the CSP is
unchanged) rather than hand-written `navigator.credentials` plumbing,
because it papers over the browsers that lack
`PublicKeyCredential.parseCreationOptionsFromJSON`. Playwright drives a
virtual authenticator through CDP (`WebAuthn.addVirtualAuthenticator`), so
CI needs no hardware; pytest uses a software authenticator written in the
tests over `cryptography`.

**The trusted-header contract.** nginx blanks every identity header on
purpose (`proxy/cabinet-proxy.conf`), so header mode cannot mean "believe
`Remote-User`". Authentik's outpost sets `X-authentik-jwt` (a JWT signed by
Authentik) and `X-authentik-meta-jwks` (where its keys are), and Traefik's
`authResponseHeaders` passes them on; Pomerium, Cloudflare Access, and
Google IAP publish an equivalent signed assertion. A signed assertion
verified against the gateway's keys, with its audience and expiry checked,
is the only header worth trusting: it binds the identity to a signature
Cabinet checks, expires on its own, and needs no long-lived secret shared
between two configs. It is passed by nginx only when the deployment names
it (section 7).

**Cabinet today, what A2 touches.** Layer 1 of the gate lets anonymous
callers reach four exact `(method, path)` pairs, checks `Sec-Fetch-Site`
on the two anonymous POSTs, and decides CSRF for cookie requests before
the session lookup. Sessions carry `auth_method` (String(16), `password`
today). The users table has a role and two external-identity columns.
The frontend boots through `GET /api/auth/state` then `GET /api/auth/me`
(`auth/AuthContext.tsx`), and `api/client.ts`'s `req()` is the one place
that reacts to a 401 or a `reauth_required` 403; `ConfirmDialog.tsx`'s
`requestConfirm()` is the one confirm dialog. Settings sections are one
file each under `pages/settings/`. Alerts go through `notify.TITLES` and
`events.record`; the audit log refuses unknown event names.

## 3. Providers: what works with plain OpenID Connect and what doesn't

| Works as-is (OpenID Connect with discovery) | Quirk to document |
|---|---|
| Authentik, Keycloak, Authelia, Zitadel, Kanidm, PocketID, Dex, FusionAuth, Ory Hydra, Casdoor, Forgejo and Gitea (as a provider), GitLab, Synology SSO Server, Nextcloud (OIDC app), Okta, Auth0, Duo SSO | Kanidm requires PKCE (Cabinet always sends it) |
| Microsoft Entra ID (free tier is enough) | Pin the tenant: `https://login.microsoftonline.com/{tenant}/v2.0`; the `common` endpoint returns a tenant issuer that fails validation. `sub` is pairwise per app, `email` optional |
| Google | Works with the discovery document at `accounts.google.com`; no groups (irrelevant here), `hd` claim for a Workspace domain not needed |
| Amazon Cognito | The issuer is the user-pool URL, not the hosted domain |
| Apple | Only without the `email`/`name` scopes: with them Apple requires `response_mode=form_post`, a cross-site POST the gate refuses (section 5). Its client secret is also a signed, rotating JWT. **Not supported** in v0.33.0 |

| Not OpenID Connect | What they are | Covered by |
|---|---|---|
| GitHub, Discord, X, Facebook, Reddit, most "Sign in with" social buttons | OAuth 2.0 without an ID token or discovery (identity read from a REST call) | The `oauth2_profile` kind (section 5a), with GitHub as the tested preset (Q9). Any other needs a preset (authorize, token, and profile URLs, the stable id field) and a live check; or an identity provider (Authentik, Keycloak) that federates them, then OpenID Connect to Cabinet |
| Shibboleth, older ADFS configurations, SAML-only enterprise setups | SAML 2.0 | Not planned. ADFS 2016 and later speak OpenID Connect; anything else through a bridging provider |
| LDAP, Active Directory, FreeIPA, LLDAP used directly | A directory, not a web sign-in | Not planned. Authentik, Keycloak, or Authelia in front of the directory |
| Cloudflare Access, Google IAP, Pomerium, Tailscale identity headers, Authentik and Authelia forward-auth, oauth2-proxy | A gateway that authenticates in front and asserts the identity in a header | The trusted-header mode (signed assertions: Authentik, Pomerium, Cloudflare Access, IAP); Authelia and oauth2-proxy sign in through their OpenID Connect side instead; Tailscale asserts plain text headers only and is not covered (see Q4) |

The generic client tolerates: `client_secret_basic` or `client_secret_post`
(read from `token_endpoint_auth_methods_supported`, basic preferred); a
public client with PKCE alone when the provider issues no secret; RS256,
PS256, ES256, and EdDSA ID tokens; `email` absent; `sub` pairwise;
60 seconds of clock skew; a provider that omits `userinfo_endpoint`. It
requires: a discovery document at `{issuer}/.well-known/openid-configuration`
whose `issuer` equals the configured one, `code` response type,
`response_mode=query`, `S256` PKCE, HTTPS (http only beside
`AUTH_INSECURE_HTTP`, for the local stack and CI's mock).

## 4. Scope

**In scope**

1. **OpenID Connect sign-in** as the admin through a linked identity:
   authorization code flow with PKCE (`S256`), `state`, and `nonce`;
   discovery; ID token validation (signature against the provider's JWKS,
   `iss`, `aud`, `exp`, `iat`, `nonce`, `azp` when several audiences);
   the identity is `(iss, sub)`, never an email. `GET /api/auth/oidc/start`
   and `GET /api/auth/oidc/callback` (section 5).
1a. **Several providers, one button each.** `auth_providers` rows (section
   8), each `oidc` or `oauth2_profile`, with presets `google`, `microsoft`
   (OpenID Connect; the issuer filled in, Microsoft asking for the tenant
   id), `github` (OAuth 2.0 profile), and `custom` (any OpenID Connect
   issuer). The sign-in page shows one button per enabled provider; the
   start route names the provider (`/api/auth/oidc/start?provider=<id>`).
2. **Linking** from Settings while signed in, with the password confirmed:
   "Link an account" runs the same flow with `intent=link`; on return the
   identity is shown (`sub`, and `email`/`preferred_username` if present)
   and stored; unlinking asks for the password again. **No first-login
   claim**: an unlinked identity that signs in at the provider gets "This
   account is not linked to Cabinet. Sign in with your password and link it
   in Settings." and an audit row.
3. **Trusted-header sign-in** from a signed assertion the deployment names
   (section 7), linked the same way ("Link the identity this proxy
   asserts"), one click on the sign-in page.
4. **Passkeys**: register (several, each named), list, rename, remove in
   Settings; second factor after the password once one exists; sign in
   with a passkey alone; confirm a fresh action with one. RP ID is the host
   of `PUBLIC_ORIGINS` (every entry must share it, checked at start;
   `WEBAUTHN_RP_ID` overrides for a sub-path deployment).
5. **Recovery**: the container's `reset-password` also removes every
   passkey and the second-factor requirement (shell access is the proof of
   ownership, as for the password); a new `unlink-identity [oidc|trusted_header]`
   command; `status` prints the linked identities, passkey count, and
   which sign-in methods are on.
6. **Sessions** from every method go into `cabinet_auth.sessions` with
   `auth_method` `password`, `passkey`, `oidc`, or `trusted_header`, the
   same cookie, lifetime, and idle rule; the known-device cookie is issued
   on every successful sign-in as today (it only ever lifts the password
   throttles).
7. **Settings → Sign-in**: a new section (`/settings/signin`) holding the
   provider configuration (issuer, client id, client secret write-only,
   scopes, display name, on/off, logout at the provider), the linked
   identities, the passkeys, and the second-factor policy. Every change is
   admin and fresh. Account keeps the password, username, sessions, tokens,
   and audit log.
8. **Audit and alerts**: events `sso_sign_in` (via the `sign_in` row's
   `detail.method`), `sso_sign_in_rejected` (unlinked identity, bad token;
   the reason, never the token), `identity_linked`, `identity_unlinked`,
   `passkey_added`, `passkey_removed`, `passkey_sign_in_failed`,
   `sso_configured` (which fields changed, never values),
   `second_factor_changed`. Alerts (webhook) for a linked or unlinked
   identity, a passkey added or removed, the provider configured, and the
   existing new-device sign-in, which now names the method.
9. **CI**: pytest with an in-process fake provider (httpx `MockTransport`)
   and a software authenticator; the compose stack with `mock_idp.py`; the
   smoke script's `sso` phase; Playwright's `sso.spec.ts` (OIDC round trip,
   link and unlink, passkey registration and 2FA through the virtual
   authenticator, header mode with the assertion set by curl).
10. **Docs**: deployment.md's section 3 rewritten (the forward-auth proxy
    becomes optional; how to configure Authentik, Keycloak, Authelia,
    Entra, Google; the header-mode contract; the share-path exemption
    stays), security.md's table and rules, api.md, roadmap, implementation
    notes, README, frontend/README, CHANGELOG, CLAUDE.md.

**Out of scope**: more accounts or group-to-role mapping; SAML; OAuth
2.0-only providers other than the GitHub preset (Q9); Google One Tap or
any provider script loaded into the page (the CSP allows no external
script, and the redirect button gives the same result); `form_post`; a
shared-secret header (Q4); a TOTP
second factor (passkeys cover it, and a TOTP secret is one more thing to
store); provider-initiated sign-in (a request arriving at the callback
without Cabinet's own state cookie is refused); back-channel or
front-channel logout from the provider (the session ends on its own idle
rule); remembering "this device needs no second factor".

## 5. The OpenID Connect flow, in detail

**Start.** `GET /api/auth/oidc/start?next=/collection[&intent=link]`
(anonymous; `intent=link` needs a fresh session and is refused otherwise).
The route makes `state` (32 random bytes), `nonce` (32), and a PKCE
verifier (43 chars), stores them with `next`, `intent`, and the session id
(for link) in a **flow cookie** `__Host-cabinet_oidc`: the JSON,
Fernet-encrypted with the app's `SECRET_KEY`, `HttpOnly`, `Secure`,
`SameSite=Lax`, `Max-Age=600`, `Path=/api/auth/oidc/`. Lax is required:
the callback is a top-level navigation from the provider's site, and a
`Strict` cookie would not be sent on it. Then `302` to the provider's
`authorization_endpoint` with `response_type=code`, `scope`,
`client_id`, `redirect_uri` (`{origin}/api/auth/oidc/callback`, the origin
from `share.link_origin`'s rule: the request's Origin if in
`PUBLIC_ORIGINS`, else the first https entry), `state`, `nonce`,
`code_challenge`, `code_challenge_method=S256`. `next` is checked by the
same rule as the sign-in page's (`safeNext`): a same-origin path only.

**Callback.** `GET /api/auth/oidc/callback?code=...&state=...`
(anonymous). In order: the flow cookie must be present and decrypt, `state`
must equal the cookie's (constant time), the cookie is cleared whatever
happens next (one use), `Sec-Fetch-Mode` if present must be `navigate` and
`Sec-Fetch-Dest` `document` (a fetch or an image can't complete a
sign-in), `error` from the provider is shown and audited (`access_denied`
is not a failure to throttle). The code is exchanged at the
`token_endpoint` (httpx, 10 s, the client secret in `Authorization: Basic`
or the body per the provider's advertised methods, `code_verifier`). The
ID token is verified: signature with `PyJWKClient` (the JWKS URI from
discovery; an unknown `kid` refetches once, at most once a minute), `alg`
in the allowed set (never `none`, never HMAC), `iss` equals the configured
issuer, `aud` contains the client id (and `azp` equals it when `aud` has
several), `exp`/`iat`/`nbf` with 60 s leeway, `nonce` equals the cookie's,
`sub` non-empty. **Nothing from the access token or userinfo decides the
identity**; `email` and `preferred_username` are read from the ID token
only for display. Then:

- `intent=login`: look up `identities(provider_id, issuer, subject)`. Found
  and the user active: `accounts.start_external(...)` creates the session
  (rotating any session the browser held, as the password sign-in does),
  sets the two cookies, audits `sign_in` with `detail.method: "oidc"`, sends
  the new-device alert if the device cookie was absent, and `303`s to
  `next`. Not found: no session, audit `sso_sign_in_rejected` with
  `reason: unlinked` (the `sub` is recorded, since it names nothing secret
  and the owner needs it to see who knocked), `303` to
  `/login?error=unlinked`.
- `intent=link`: the flow cookie's session id must be the current
  session's and still fresh; the identity must not already be linked (409
  otherwise); insert the `identities` row, audit and alert
  `identity_linked`, `303` to `/settings/signin?linked=oidc`.

Failures a caller can cause (missing cookie, bad state, provider error,
token validation) redirect to `/login?error=<short code>` with the reason
in the audit row, never the token or the code. The callback is throttled
per address by the existing `throttle` map under a new kind `oidc` (20
free in 15 minutes, then a wait), counting failures only.

**Why the gate can allow it.** Both routes are anonymous `GET`s added to
`gate.ANONYMOUS`. The callback is by nature `Sec-Fetch-Site: cross-site`,
and the gate today checks `Sec-Fetch-Site` only on the two anonymous
POSTs, so no gate rule changes; CSRF for the callback is the `state`
bound to the flow cookie, which a cross-site page can't read or set. The
callback **sets** a session cookie, so login CSRF is considered: an
attacker who starts a flow and hands the victim's browser the callback URL
fails on `state` (the victim's browser has no flow cookie, or one with a
different state). The start route redirects and reads no body; it is
reachable cross-site (a link from anywhere), which is fine: it only ever
sends the browser to the configured provider.

**Logs.** The code and state sit in the callback's query string.
`main._configure_logging`'s `uvicorn.access` filter (from v0.32.0) gains a
rule turning `/api/auth/oidc/callback?...` into
`/api/auth/oidc/callback?[redacted]`, and nginx's `map` gains the same
line. A test pins both.

**Discovery and keys** are cached in memory per process (discovery 24 h,
JWKS by PyJWT's own cache), fetched lazily on the first start, so
switching the provider on makes no request until someone signs in. A
provider that can't be reached at sign-in time is a 502 page
("The identity provider did not answer. Sign in with your password.").
Every outbound call has a 10 s timeout, follows no redirects, and sends
nothing but the protocol's own parameters (security.md's outbound list
gains the provider).

**Confirming a fresh action** (Q1) reuses the flow with `intent=confirm`,
adding `prompt=login&max_age=0`; on return `auth_time` must be within 120 s,
the session's `confirmed_until` opens, `303` back to `next`. The confirm
dialog offers "Confirm at <provider>" on an `oidc` session, a passkey on
any session that has one, and the password always; `FreshLink` learns the
same choice.

## 5a. The `oauth2_profile` kind, and the GitHub preset

The same routes, flow cookie, `state`, PKCE, throttle, and audit rows as
section 5; what differs is after the code exchange. There is no ID token,
so `app/auth/oidc.py` asks the provider's **profile endpoint** with the
access token (`Authorization: Bearer`, `Accept: application/json`, 10 s,
no redirects) and reads the stable identifier from the JSON at the path
the preset names. The identity is `(issuer, subject)` with the preset's
fixed issuer string, so it lives in the same `identities` table and links
the same way. `nonce` is not sent (nothing would carry it back), which is
why `state` in the one-use cookie is the whole CSRF defence here as well.
A preset is data, not code:

| Preset | Authorize | Token | Profile | Subject | Display | Issuer string | Scopes |
|---|---|---|---|---|---|---|---|
| `github` | `https://github.com/login/oauth/authorize` | `https://github.com/login/oauth/access_token` | `https://api.github.com/user` | `id` (a number, stable for the account's life; `login` can change and is never used) | `login` | `https://github.com` | `read:user` |

Rules: the token response must be JSON (GitHub answers form-encoded
without the `Accept` header, which is the classic mistake) and carry
`access_token` with `token_type` `bearer`; the access token is used for
that one profile call and then dropped, never stored; a profile without
the subject field, or a non-numeric GitHub `id`, is a failure
(`sso_sign_in_rejected`, `reason: profile`). GitHub's OAuth app
registration needs the callback URL `{origin}/api/auth/oidc/callback`
(one per app; a second origin needs a second GitHub app). GitHub's
`email` is not requested: it is not needed for the identity and asks the
user for more than sign-in warrants. A second `oauth2_profile` preset
(Discord: `id`, `identify` scope) is a table row and a live check, not a
design change, and is not in v0.33.0 (Q9).

## 6. Passkeys

**Tables** (`a0002`): `passkeys` (`id`, `user_id` FK, `credential_id`
bytes unique, `public_key` bytes, `sign_count` int, `transports` JSON,
`aaguid` bytes, `name` String(60), `backup_eligible`, `backed_up`,
`created_at`, `last_used_at`). `auth_config.second_factor` (`off` |
`passkey`), set to `passkey` automatically when the first passkey is
registered and back to `off` when the last is removed or by the reset
command.

**Registration** (admin, fresh): `POST /api/auth/passkeys/options` returns
`PublicKeyCredentialCreationOptions` (RP ID from section 4 item 4, user
handle a random 32 bytes stored once per user, `residentKey: preferred`,
`userVerification: preferred`, `excludeCredentials` the existing ones,
attestation `none`) and keeps the challenge in a `__Host-cabinet_webauthn`
cookie (Fernet, 5 minutes, `Path=/api/auth/passkeys/`, `SameSite=Strict`);
`POST /api/auth/passkeys` verifies with `webauthn.verify_registration_response`
against the challenge, `PUBLIC_ORIGINS` (all of them as allowed origins),
and the RP ID, stores the row, audits and alerts.

**Second step after the password.** `POST /api/auth/login` with a right
password on an account whose `second_factor` is `passkey` answers `200
{"second_factor": "passkey"}` and sets a **pending cookie**
`__Host-cabinet_pending` (Fernet: user id, the device-cookie decision,
`next`; 5 minutes; `Path=/api/auth/passkey/`) instead of a session. `POST
/api/auth/passkey/options` (anonymous, needs the pending cookie) returns
the assertion options with `allowCredentials` for that user; `POST
/api/auth/passkey/verify` (anonymous, pending cookie) checks the assertion
(`verify_authentication_response`, sign count must not go backwards unless
the stored count is 0), clears the pending cookie, and finishes the sign-in
exactly as the password path does. Both anonymous POSTs join `SMALL_BODY`
(8 KiB, `Sec-Fetch-Site` cross-site refused) and are throttled like
sign-in (`throttle.attempt` on the user and address). A wrong assertion
is `sign_in_failed` with `detail.step: passkey`.

**Passkey alone.** The sign-in page's "Sign in with a passkey" calls the
same two routes without a pending cookie: `options` returns a discoverable
credential request (`allowCredentials` empty), `verify` finds the row by
`credential_id`, requires `userVerification: required` (the authenticator
checked a PIN or biometric, which is the second factor), and starts the
session with `auth_method: passkey`. Also throttled per address.

**Confirm** with a passkey: `POST /api/auth/confirm/passkey/options` and
`/verify` (admin) open `confirmed_until` the way the password does.

**Recovery.** A lost passkey with the password still known: sign in with
the password, then the OpenID Connect path if linked, or the container's
`reset-password`, which removes all passkeys. Nothing else: no recovery
codes (one more secret to store and phish; the shell is the recovery).

## 7. The trusted-header mode

**Deployment contract.** Three environment variables on the backend, and
one of them on the proxy:

| Variable | Meaning |
|---|---|
| `TRUSTED_ASSERTION_HEADER` | The header carrying the gateway's signed JWT (`X-authentik-jwt`, `Cf-Access-Jwt-Assertion`, `X-Pomerium-Jwt-Assertion`, `X-Goog-IAP-JWT-Assertion`). Set on **both** backend and proxy; unset, the mode is off and nginx blanks every identity header as today |
| `TRUSTED_ASSERTION_JWKS_URL` | Where the gateway's public keys are (Authentik: the provider's `jwks/` URL, also announced in `X-authentik-meta-jwks`; Cloudflare: `https://<team>.cloudflareaccess.com/cdn-cgi/access/certs`; Pomerium: `https://<authenticate>/.well-known/pomerium/jwks.json`; IAP: `https://www.gstatic.com/iap/verify/public_key-jwk`) |
| `TRUSTED_ASSERTION_ISSUER` and `TRUSTED_ASSERTION_AUDIENCE` | Required `iss` and `aud` (Authentik: the provider's issuer and client id; Cloudflare: the team domain and the application's AUD tag) |

`config.check_startup` refuses a partial set. The header name is checked
against `^[A-Za-z][A-Za-z0-9-]{1,60}$` and must not be one of the
forwarded-address headers.

**nginx.** `proxy/40-cabinet-hosts.sh` (renamed `40-cabinet-config.sh`)
writes `cabinet-identity.conf` at start: every identity header in today's
list set to `""`, except the one `TRUSTED_ASSERTION_HEADER` names, written
as `proxy_set_header <Name> $http_<name_with_underscores>;`, and every
proxied location includes it (the list moves out of `cabinet-proxy.conf`
into the generated file; a test greps that no location lacks the include).
So the assertion reaches the backend only when the deployment says so, and
nothing else ever does.

**Backend.** `GET /api/auth/state` reports `trusted_header: {available:
true, name: <display name from the assertion, if any>}` only when the mode
is on **and** the request carries an assertion that verifies (signature
against `TRUSTED_ASSERTION_JWKS_URL` with `PyJWKClient`, `iss`, `aud`,
`exp`, `nbf`, 60 s leeway; never `none` or HMAC). `POST /api/auth/trusted`
(anonymous, no body, `Sec-Fetch-Site` cross-site refused, throttled per
address) verifies the assertion again, looks up
`identities(kind='trusted_header', issuer, subject)`, and starts the
session (`auth_method: trusted_header`) or answers 403 `unlinked` with an
audit row. Linking: "Link the identity this proxy asserts" in Settings
(admin, fresh) reads the current request's assertion and stores its
`(iss, sub)`. **A request's assertion never authenticates a route on its
own**: it is consulted only by `state`, `trusted`, and the link route, and
only to start a session. Replay of a captured assertion is bounded by its
`exp` (Authentik's are minutes); the header only ever travels
gateway → nginx → backend on the internal network, and the same holds for
the session cookie.

**Why not `Remote-User` with a secret** is question 4.

## 8. Data model (`a0002`)

- `auth_providers`: `id`, `kind` (`oidc` | `oauth2_profile`, check),
  `preset` (`google` | `microsoft` | `github` | `custom`), `display_name`
  String(60), `enabled`, `issuer` String(255) (the OpenID Connect issuer,
  or the preset's fixed issuer string), `client_id` String(255),
  `client_secret` (Fernet text, write-only through the API), `scopes`
  String(255), `logout_at_provider`, `created_at`, `updated_at`; unique
  `(issuer, client_id)`. At most 8 rows. A `custom` row is `oidc`; the
  URLs of an `oauth2_profile` row come from the preset table in code, so
  the database never holds an authorize or profile URL a client chose.
- `identities`: `id`, `user_id` FK cascade, `kind` (`provider` |
  `trusted_header`, check), `provider_id` FK cascade nullable (set for
  `provider`), `issuer` String(255), `subject` String(255), `display`
  String(120) nullable (email or username at link time, for the Settings
  list only), `linked_at`, `last_used_at`; unique `(user_id, provider_id)`
  (one identity per provider), one `trusted_header` row per user (a
  partial unique index), and unique `(issuer, subject)`. Deleting a
  provider row deletes its identity.
- `passkeys` as in section 6, plus `users.webauthn_handle` bytes(32)
  nullable.
- `auth_config` (singleton, `id = 1` check): `second_factor`,
  `require_passkey_for_sso`, `updated_at`. Read with the provider rows
  through `app/auth/config.py`, cached per process and reloaded on write
  (one replica, as documented).
- Drop `users.external_issuer` and `users.external_subject` (Q5).
- `sessions.auth_method` already fits the four values.
- Nothing in `public` changes: **no collection migration** in v0.33.0.

## 9. The gate, layer by layer

Layer 1 gains these anonymous pairs: `GET /api/auth/oidc/start`,
`GET /api/auth/oidc/callback`, `POST /api/auth/trusted`,
`POST /api/auth/passkey/options`, `POST /api/auth/passkey/verify`. The
three POSTs join `SMALL_BODY`. No other gate rule changes: the maintenance
rule, the share prefix, the token rules, and CSRF for cookie requests stay
as they are. Layer 2: every new route declares its class (table below),
and `test_gate.py`'s appendix parser reads SPEC_0330's table as well as
SPEC_0300's. The anonymous matrix grows by five pairs; the encoding,
scope, fresh, and CSRF matrices run over the new routes for free.

**New routes**

| Method | Path | Class | Note |
|---|---|---|---|
| GET | `/api/auth/oidc/start` | public | `provider=<id>`; 302 to that provider; sets the flow cookie; 404 for an unknown or disabled provider; `intent=link` or `confirm` needs a fresh session (403 otherwise) |
| GET | `/api/auth/oidc/callback` | public | 303 to `next` or `/login?error=`; one-use flow cookie; throttled on failure |
| POST | `/api/auth/trusted` | public | Starts a session from a verified assertion; 404 when the mode is off; 403 unlinked; 8 KiB |
| POST | `/api/auth/passkey/options` | public | Assertion options; pending cookie or discoverable; 8 KiB |
| POST | `/api/auth/passkey/verify` | public | Finishes a 2FA or passkey-only sign-in; 8 KiB |
| GET | `/api/auth/signin-config` | admin | The providers (secrets masked), the linked identities, passkeys, policy, and the preset list |
| PUT | `/api/auth/signin-config` | admin, fresh | Change the policy; audited (`second_factor_changed`) |
| POST | `/api/auth/providers` | admin, fresh | Add a provider from a preset or a custom issuer; `dry_run` fetches discovery only; audited (`sso_configured`), alerted |
| PATCH | `/api/auth/providers/{id}` | admin, fresh | Change it (a secret is replaced, never read back); audited, alerted |
| DELETE | `/api/auth/providers/{id}` | admin, fresh | Remove it and its linked identity; audited, alerted |
| DELETE | `/api/auth/identities/{id}` | admin, fresh | Unlink; audited, alerted |
| POST | `/api/auth/identities/trusted_header` | admin, fresh | Link the current request's assertion |
| POST | `/api/auth/passkeys/options` | admin, fresh | Registration options; challenge cookie |
| POST | `/api/auth/passkeys` | admin, fresh | Register; audited, alerted |
| PATCH | `/api/auth/passkeys/{id}` | admin, fresh | Rename |
| DELETE | `/api/auth/passkeys/{id}` | admin, fresh | Remove; the last one turns the second factor off; audited, alerted |
| POST | `/api/auth/confirm/passkey/options` | admin | Confirm with a passkey, step 1 |
| POST | `/api/auth/confirm/passkey/verify` | admin | Step 2; opens the window |

**Changed routes**: `GET /api/auth/state` adds `methods: {password: true,
passkey: bool, providers: [{id, name, preset}], trusted_header:
{available, name} | null}`; `POST /api/auth/login` may answer `{"second_factor": "passkey"}`
with the pending cookie and no session; `GET /api/auth/me` adds
`auth_method` and `confirm_methods`; `POST /api/auth/logout` on an `oidc`
session with logout-at-provider on answers `{"redirect": <end_session
URL>}` for the frontend to follow.

## 14. Risks and open items

- **The callback is the first cross-site navigation that sets a session
  cookie.** Its safety rests on the `state` in an encrypted, one-use,
  path-scoped cookie and on refusing anything that isn't a top-level
  navigation. The review should read `oidc.callback` first.
- **A provider that publishes HMAC or `none` algorithms** is ignored: the
  allowed set is fixed in code.
- **Clock skew** at the homelab: 60 s leeway; a further-off clock fails
  with a clear message naming the skew.
- **Multiple `PUBLIC_ORIGINS` hosts** break passkeys (one RP ID); refused
  at start unless `WEBAUTHN_RP_ID` names a common parent, with the message
  saying so.
- **Numista confirmation and the other v1.0.0 items** are unaffected;
  v0.33.0 adds no collection migration.
