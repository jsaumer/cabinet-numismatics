# SPEC_0330: Cabinet v0.33.0, single sign-on (P8 A2)

Status: **approved by the owner on 24 September 2026**: every
recommendation in section 1 taken as written (section 15 lists the
answers), then **reviewed in two rounds before any code** (Codex and a
fresh-context Claude Opus review in each round, the same day; sections 16
and 17 record every finding and its verdict, and the rules taken are
folded into the sections below, marked with the finding's id: CR-nn and
SSO-nn from round one, R2-nn from round two). Planned the day after v0.32.2 shipped, as the last item of
roadmap Phase 7 before the road to v1.0.0. Built on `p8-auth-a2`, stage
by stage (section 13); a fresh-context security review before the
release, as for A1 and P9.

## Why

Since v0.30.0 the admin signs in with a username and a password, and the
recommended deployment keeps an authenticating reverse proxy in front as a
second door, because Cabinet's own sign-in has no second factor and no way
to reuse the identity the homelab already has. A2 closes that: the same
admin signs in through an OpenID Connect provider (or GitHub), or through
the identity a forward-auth proxy has already checked, and the **second
factor is the provider's own** (the owner's decision, 24 September 2026:
no passkeys or other MFA inside Cabinet, so there is no second credential
store to manage or recover). The password stays as the recovery
credential, so an outage at the provider can never lock the owner out and
the container's break-glass reset keeps working; the deployment doc says,
sternly, what that single-factor fallback means for exposure (section 12).

What is settled and not reopened here (the owner's decisions of 20 and 21
September 2026): one admin and one collection; login always on; the
deny-by-default gate with `@permission` classes, enforced by
`tests/test_gate.py` against SPEC_0300's appendix; sessions in
`cabinet_auth` (next revision `a0002`); nginx trusts no forwarded header
and blanks identity headers; the local password stays; more accounts are
not part of A2.

## 1. The owner's questions

Answer these first; everything below is written to the recommended answer
and changes where a different one is chosen.

1. **Where the "password again" comes from on a single sign-on session.**
   Today a fresh action asks for the local password. Recommended: a session
   confirms with the method it signed in by. A password session types the
   password (as today); a provider session is sent back to the provider
   with `prompt=login` and `max_age=0` and passes when the new ID token's
   `auth_time` is under two minutes old (a GitHub session, which has no ID
   token and no `prompt`, types the password); a trusted-header session,
   which the proxy can't step up, types the password. The password always
   works on any session. Alternative, simpler: the password on every kind
   of session (one dialog, no new flow), at the cost of an SSO-only owner
   still needing to remember it.
2. **Second factor.** Decided by the owner on 24 September 2026: **the
   provider's MFA is the second factor; Cabinet builds none of its own.**
   No passkeys, TOTP, or recovery codes in v0.33.0 (passkeys stay on the
   roadmap as an optional later item). The password path is therefore one
   factor, hardened as in A1 (Argon2id, throttles, the known-device cookie,
   the new-device alert), and the deployment doc treats it as a recovery
   credential (section 12). One addition for that: a switch
   `password_sign_in_alerts` (off) that alerts on **every** password
   sign-in, not only from a new browser, as a tripwire on the fallback
   door. Left to confirm: whether it should default to **on** whenever at
   least one provider is enabled (recommended: yes, since the password is
   then meant to be rare).
3. **How a trusted-header sign-in starts.** Recommended: one click on the
   sign-in page ("Continue with the proxy's sign-in"; R2-03 took the
   name out, since showing it meant verifying an assertion on every
   anonymous boot request), never
   automatic, so signing out of Cabinet means something while the proxy
   session lives on. Alternative: automatic when the proxy asserts an
   identity and no Cabinet session exists (fewer clicks, but sign-out
   bounces straight back in).
4. **Shared-secret header mode: build it, or signed assertions only.**
   Recommended: **signed assertions only** in v0.33.0 (Authentik's
   `X-authentik-jwt`, Pomerium's `X-Pomerium-Jwt-Assertion`, Cloudflare
   Access's `Cf-Access-Jwt-Assertion`, Google IAP's
   `X-Goog-IAP-JWT-Assertion`: each a JWT the gateway signs and Cabinet
   verifies against the gateway's published keys). A shared-secret header
   (`Remote-User` plus a static secret the proxy adds) proves only that the
   request passed through the proxy, and whoever holds the secret is the
   admin: it is a second password on the wire. Authelia and oauth2-proxy
   users would then sign in through **OpenID Connect** instead, which both
   provide. Alternative: add the shared-secret mode as a third path, never
   able to confirm a fresh action.
5. **One linked identity, or one per provider.** Recommended: an
   `identities` table allowing one identity per configured provider plus
   one for the trusted-header mode (Q9 widened this from one per mode),
   since a homelab may run the proxy against one provider and sign in
   through Google or GitHub as well, and drop the two unused `users` columns
   (`external_issuer`, `external_subject`, null everywhere today) in
   `a0002`. Alternative: keep the columns and allow exactly one identity.
6. **Where the provider configuration lives.** Recommended: in
   `cabinet_auth` (a single-row `auth_config` table), not `app_settings`,
   because how the admin signs in is deployment state the way the admin's
   password is: a restore never changes it, an archive never carries the
   client secret, and there is no put-back dance as with share links. The
   client secret is Fernet-encrypted with the same key as the API keys.
   Alternative: `app_settings` keys (carried by backups, put back after a
   restore like share links).
7. **Logout at the provider.** Recommended: local only by default, plus an
   optional "also sign out at the provider" (RP-initiated logout through
   `end_session_endpoint`, if the provider publishes one) as a switch, off.
   As built it sends `client_id` and a registered
   `post_logout_redirect_uri` (the ID token is not kept, so no
   `id_token_hint`), or several providers show a confirmation page or
   refuse (review add list).
8. **The mock provider for CI.** Recommended: a ~200-line stdlib Python
   OpenID Connect provider in `scripts/ci/mock_idp.py`, run as one more
   service in a CI-only compose override, auto-approving with a chosen
   subject and able to misbehave on request (wrong nonce, expired token,
   wrong audience, unknown key), so the smoke script and Playwright can test
   the failures too. Alternative: `dexidp/dex` with static passwords (a real
   provider, more faithful, but no way to make it misbehave).
9. **Sign-in buttons for GitHub and the like.** Decided by the owner on
   24 September 2026: **in scope.** GitHub is OAuth 2.0 without an ID
   token, so Cabinet gains a second provider kind, `oauth2_profile`, that
   reads the identity from the provider's profile endpoint after the code
   exchange (section 5a), with GitHub as its one tested preset. Presets
   for Google and Microsoft (plain OpenID Connect, no new code) fill the
   issuer for the owner. Several providers can be configured at once, one
   button each, and the admin can link one identity per provider. Left to
   confirm: whether Discord should join GitHub as a second
   `oauth2_profile` preset (recommended: not now; the kind is generic, a
   preset is a few lines and a live check later).

## 2. What the research found

**Providers.** OpenID Connect is one protocol; every mainstream identity
provider speaks it, and Cabinet gains nothing provider-specific. What
differs is quirks a generic client has to tolerate, and a short list of
services that are not OpenID Connect providers at all (section 3).

**The library.** Three candidates for the OpenID Connect client:

- `authlib`: a full client, but its Starlette integration wants Starlette's
  `SessionMiddleware` (a signed cookie session Cabinet doesn't have) and
  its lower-level `OAuth2Session` hides exactly the steps a review has to
  read (state, nonce, PKCE, token validation).
- `joserfc` (the same author, newer): JWT and JWKS only, well maintained.
- **`PyJWT` (recommended)**: JWT verification with `PyJWKClient` for the
  provider's key set (a two-tier cache, refetched on an unknown `kid`),
  RS256/PS256/ES256/EdDSA through `cryptography`, which is already in the
  lockfile. PyJWT 2.14 is current and Debian-packaged.

The flow itself (discovery, the authorization redirect, the code exchange
over `httpx`, which Cabinet already has) is about 300 lines written by hand
in `app/auth/oidc.py`, so every step is readable in one file, as the gate
and the password check are. The only provider-specific parts are the
preset table's URLs and field names (section 5a); no provider gets code of
its own.

**Passkeys, researched and set aside.** `webauthn` (py_webauthn, Duo
Labs, June 2026) on the server, `@simplewebauthn/browser` (v14) in the
page, a CDP virtual authenticator in Playwright: workable, about a third
of the build, and dropped on 24 September 2026 in favour of the
provider's MFA (Q2). The notes stay here for the day passkeys are wanted:
the RP ID would be the host of `PUBLIC_ORIGINS`, so every entry would have
to share one host.

**The trusted-header contract.** nginx blanks every identity header on
purpose (`proxy/cabinet-proxy.conf`), so header mode cannot mean "believe
`Remote-User`". Authentik's outpost sets `X-authentik-jwt` (a JWT signed by
Authentik) and `X-authentik-meta-jwks` (where its keys are), and Traefik's
`authResponseHeaders` passes them on; Pomerium, Cloudflare Access, and
Google IAP publish an equivalent signed assertion. A signed assertion
verified against the gateway's keys, with its audience and expiry checked,
is the only header worth trusting: it binds the identity to a signature
Cabinet checks, expires on its own, and needs no long-lived secret shared
between two configs. It is passed by nginx only when the deployment names
it (section 7).

**Cabinet today, what A2 touches.** Layer 1 of the gate lets anonymous
callers reach four exact `(method, path)` pairs, checks `Sec-Fetch-Site`
on the two anonymous POSTs, and decides CSRF for cookie requests before
the session lookup. Sessions carry `auth_method` (String(16), `password`
today). The users table has a role and two external-identity columns.
The frontend boots through `GET /api/auth/state` then `GET /api/auth/me`
(`auth/AuthContext.tsx`), and `api/client.ts`'s `req()` is the one place
that reacts to a 401 or a `reauth_required` 403; `ConfirmDialog.tsx`'s
`requestConfirm()` is the one confirm dialog. Settings sections are one
file each under `pages/settings/`. Alerts go through `notify.TITLES` and
`events.record`; the audit log refuses unknown event names.

## 3. Providers: what works with plain OpenID Connect and what doesn't

| Works as-is (OpenID Connect with discovery) | Quirk to document |
|---|---|
| Authentik, Keycloak, Authelia, Zitadel, Kanidm, PocketID, Dex, FusionAuth, Ory Hydra, Casdoor, Forgejo and Gitea (as a provider), GitLab, Synology SSO Server, Nextcloud (OIDC app), Okta, Auth0, Duo SSO | Kanidm requires PKCE (Cabinet always sends it) |
| Microsoft Entra ID (free tier is enough) | Pin the tenant: `https://login.microsoftonline.com/{tenant}/v2.0`; the `common` endpoint returns a tenant issuer that fails validation. `sub` is pairwise per app, `email` optional |
| Google | Works with the discovery document at `accounts.google.com`; no groups (irrelevant here), `hd` claim for a Workspace domain not needed |
| Amazon Cognito | The issuer is the user-pool URL, not the hosted domain |
| Apple | Only without the `email`/`name` scopes: with them Apple requires `response_mode=form_post`, a cross-site POST the gate refuses (section 5). Its client secret is also a signed, rotating JWT. **Not supported** in v0.33.0 |

| Not OpenID Connect | What they are | Covered by |
|---|---|---|
| GitHub, Discord, X, Facebook, Reddit, most "Sign in with" social buttons | OAuth 2.0 without an ID token or discovery (identity read from a REST call) | The `oauth2_profile` kind (section 5a), with GitHub as the tested preset (Q9). Any other needs a preset (authorize, token, and profile URLs, the stable id field) and a live check; or an identity provider (Authentik, Keycloak) that federates them, then OpenID Connect to Cabinet |
| Shibboleth, older ADFS configurations, SAML-only enterprise setups | SAML 2.0 | Not planned. ADFS 2016 and later speak OpenID Connect; anything else through a bridging provider |
| LDAP, Active Directory, FreeIPA, LLDAP used directly | A directory, not a web sign-in | Not planned. Authentik, Keycloak, or Authelia in front of the directory |
| Cloudflare Access, Google IAP, Pomerium, Tailscale identity headers, Authentik and Authelia forward-auth, oauth2-proxy | A gateway that authenticates in front and asserts the identity in a header | The trusted-header mode (signed assertions: Authentik, Pomerium, Cloudflare Access, IAP); Authelia and oauth2-proxy sign in through their OpenID Connect side instead; Tailscale asserts plain text headers only and is not covered (see Q4) |

The generic client tolerates: `client_secret_basic` or `client_secret_post`
(read from `token_endpoint_auth_methods_supported`, basic preferred); a
public client with PKCE alone when the provider issues no secret; RS256,
PS256, ES256, and EdDSA ID tokens; `email` absent; `sub` pairwise;
60 seconds of clock skew; a provider that omits `userinfo_endpoint`. It
requires: a discovery document at `{issuer}/.well-known/openid-configuration`
whose `issuer` equals the configured one, `code` response type,
`response_mode=query`, `S256` PKCE, HTTPS (http only beside
`AUTH_INSECURE_HTTP`, for the local stack and CI's mock).

## 4. Scope

**In scope**

1. **OpenID Connect sign-in** as the admin through a linked identity:
   authorization code flow with PKCE (`S256`), `state`, and `nonce`;
   discovery; ID token validation (signature against the provider's JWKS,
   `iss`, `aud`, `exp`, `iat`, `nonce`, `azp` when several audiences);
   the identity is `(iss, sub)`, never an email. `GET /api/auth/oidc/start`
   and `GET /api/auth/oidc/callback` (section 5).
1a. **Several providers, one button each.** `auth_providers` rows (section
   8), each `oidc` or `oauth2_profile`, with presets `google`, `microsoft`
   (OpenID Connect; the issuer filled in, Microsoft asking for the tenant
   id), `github` (OAuth 2.0 profile), and `custom` (any OpenID Connect
   issuer). The sign-in page shows one button per enabled provider; the
   start route names the provider (`/api/auth/oidc/start?provider=<id>`).
2. **Linking** from Settings while signed in, with the password confirmed:
   "Link an account" runs the same flow with `intent=link`; on return the
   identity is shown (`sub`, and `email`/`preferred_username` if present)
   and stored; unlinking asks for the password again. **No first-login
   claim**: an unlinked identity that signs in at the provider gets "This
   account is not linked to Cabinet. Sign in with your password and link it
   in Settings." and an audit row.
3. **Trusted-header sign-in** from a signed assertion the deployment names
   (section 7), linked the same way ("Link the identity this proxy
   asserts"), one click on the sign-in page.
4. **The second factor is the provider's** (Q2). Cabinet stores no second
   credential. `password_sign_in_alerts` in `auth_config` alerts on every
   password sign-in when on.
5. **Recovery**, all from the container (shell access is the proof of
   ownership, as for the password): `reset-password` as today (every
   session and token ended, throttles cleared); a new `unlink-identity
   <id>` command; a new `disable-sso` command that turns every provider
   and the trusted-header mode off in one step, for a configuration that
   interferes with the sign-in page (a proxy redirect loop, say); `status`
   prints the providers, the linked identities, and which sign-in methods
   are on. **The commands take effect in the running backend at once**
   (R2-01): provider rows and `auth_config` are **not cached**; the
   backend reads them from the database on every use (the state route,
   start, callback, `trusted`, the link routes), a few rows on a rare
   request, so a write from the container's own process is seen by the
   next request, with no restart and no flag file. **The trusted-header
   mode has a stored switch** (R2-02, Codex R2-01):
   `auth_config.trusted_header_enabled`, true by default so a deployment
   that sets the four variables works with no extra step; `disable-sso`
   sets it false in the same transaction that disables every provider and
   revokes every `oidc` and `trusted_header` session, and `state`,
   `POST /api/auth/trusted`, and the header link route all treat the mode
   as off while it is false, whatever the environment says. Switching it
   back on is a Settings action (admin, fresh, audited as
   `sso_configured`). **Removing a way in ends the sessions that came through it**
   (Q12): deleting a provider, unlinking an identity, and `disable-sso`
   each revoke every live session whose `auth_method` and provider match
   (`disable-sso`: every `oidc` and `trusted_header` session), the way a
   password change already ends everything. **Provider ids and secrets
   are not in backups** (they live in `cabinet_auth`, Q6): Settings →
   Sign-in says so, and backup-restore.md's list of what to keep outside
   Cabinet (the backup key, the setup code) gains them; a restore onto a
   fresh machine means re-entering them and relinking, as for the
   password. **The browser never sets a new password without the current
   one**, on a provider session included: a compromised GitHub or Google
   account must not become a changed Cabinet password. A forgotten password
   is always the container command, SSO or not, and the deployment doc says
   so.
6. **Sessions** from every method go into `cabinet_auth.sessions` with
   `auth_method` `password`, `oidc`, or `trusted_header`, the
   same cookie, lifetime, and idle rule. **The known-device cookie is
   issued only by a successful password sign-in or password confirm**
   (CR-03): an SSO or header sign-in issues none and leaves an existing one
   alone, since the device cookie lifts the password throttles and gives
   five reserved Argon2 checks, and a provider account or a replayed
   assertion must never buy unthrottled guesses at the recovery password.
   The new-device alert on an SSO or header sign-in is decided by a
   **browser cookie with no role in authentication or throttling**
   (R2-04, Codex R2-03): `__Host-cabinet_browser` (bare name under
   `AUTH_INSECURE_HTTP`), 32 random bytes stored as a hash with the user
   id in a new `known_browsers` table, `HttpOnly`, `Secure`,
   **`SameSite=Lax`** so that, unlike the Strict device cookie, it is sent
   on the cross-site callback, 90 days, issued on every successful sign-in
   of any method if absent. The alert fires when the sign-in carries no
   valid browser cookie. It is never read by `devices`, `throttle`, or
   `_check_password`, and never lifts anything; an address was rejected as
   the key because behind a Swarm ingress every browser shares the
   gateway's address. `sign_out_everywhere`, a password change, and
   `reset-password` delete the rows, so the next sign-in from anywhere
   alerts.
7. **Settings → Sign-in**: a new section (`/settings/signin`) holding the
   provider configuration (issuer, client id, client secret write-only,
   scopes, display name, on/off, logout at the provider), the linked
   identities, and the alert switch. Every change is admin and fresh. Account keeps the password, username, sessions, tokens,
   and audit log.
8. **Audit and alerts**: events `sso_sign_in` (via the `sign_in` row's
   `detail.method`), `sso_sign_in_rejected` (unlinked identity, bad token;
   the reason, never the token), `identity_linked`, `identity_unlinked`,
   `sso_configured` (which fields changed, never values),
   `sso_disabled` (the container command). Alerts (webhook) for a linked
   or unlinked identity, a provider added, changed, or removed, SSO
   disabled from the container, the existing new-device sign-in (which now
   names the method), and, with `password_sign_in_alerts` on, every
   password sign-in. **`sso_sign_in_rejected` has a cap of its own**
   (R2-05): like `sign_in_failed`, at most 10,000 rows, trimmed as they
   are written, so that anyone with a Google or GitHub account completing
   the flow as an unlinked `sub` can never push `password_changed`,
   `token_created`, or a restore row out of the shared 50,000; its stdout
   lines are sampled the way failures are; and a burst of them (20 in 15
   minutes) alerts once an hour through `notify`, as password failures
   do. **A provider that rejects Cabinet's credentials** (`invalid_client`
   or `unauthorized_client` at the token endpoint, GitHub's own
   `incorrect_client_credentials` for the `github` preset, and any token
   response carrying `error` whatever its status, since GitHub answers
   200 with an error body, R2-12; an expired Entra client secret looks
   like this; Google's and GitHub's don't expire) is a condition, not an
   event (Q13):
   `alerts.fail`/`recover` under `sso_provider_<id>`, so it alerts once
   when it starts, recovers when a sign-in succeeds, shows on the
   provider's row in Settings, and appears in `cabinet_alert_failing`.
9. **CI**: pytest with an in-process fake provider (httpx `MockTransport`);
   the compose stack with `mock_idp.py`; the smoke script's `sso` phase;
   Playwright's `sso.spec.ts` (OIDC and GitHub round trips, link and
   unlink, header mode with the assertion set by curl).
10. **Docs**: deployment.md's section 3 rewritten (the forward-auth proxy
    becomes optional; how to configure Authentik, Keycloak, Authelia,
    Entra, Google, GitHub; the header-mode contract; the share-path
    exemption stays) **plus a new exposure section** (section 12: Cabinet
    is for private networks and is **not to be exposed to the internet**;
    reach it from outside over a VPN or an identity-aware tunnel only; the
    password as a recovery credential), security.md's table and rules,
    api.md, roadmap, implementation notes, README, frontend/README,
    CHANGELOG, CLAUDE.md.

**Out of scope**: more accounts or group-to-role mapping; SAML; OAuth
2.0-only providers other than the GitHub preset (Q9); Google One Tap or
any provider script loaded into the page (the CSP allows no external
script, and the redirect button gives the same result); `form_post`; a
shared-secret header (Q4); any second factor inside Cabinet (passkeys,
TOTP, recovery codes: Q2); a switch that turns the password off (never:
it is the recovery credential); setting a new password from the browser
without the current one; provider-initiated sign-in (a request arriving
at the callback without Cabinet's own state cookie is refused);
back-channel or front-channel logout from the provider (the session ends
on its own idle rule).

## 5. The OpenID Connect flow, in detail

**Start.** `GET /api/auth/oidc/start?next=/collection[&intent=link]`
(anonymous; `intent=link` needs a fresh session and is refused otherwise).
The route makes `state` (32 random bytes), `nonce` (32), and a PKCE
verifier (43 chars), stores them with `next`, `intent`, and the session id
(for link and confirm: the **hash of the session secret**, not the
session id, CR-01) in a **flow cookie** `__Host-cabinet_oidc`: the JSON
(with `"purpose": "oidc_flow"`, checked on decrypt, CR-17), Fernet-encrypted
with the app's `SECRET_KEY` and decrypted with `ttl=600`, `HttpOnly`,
`Secure`, `SameSite=Lax`, `Max-Age=600`, **`Path=/`** (CR-06: a `__Host-`
cookie is ignored by browsers unless its path is `/`, rfc6265bis section
4.1.3.2; the path added nothing, since the cookie is encrypted and read
only by the OIDC routes). Under `AUTH_INSECURE_HTTP` it is the bare name
`cabinet_oidc` without `Secure`, from the same helper as
`sessions.cookie_names`. Lax is required: the callback is a top-level
navigation from the provider's site, and a `Strict` cookie would not be
sent on it. Then `302` to the provider's `authorization_endpoint` with
`response_type=code`, `scope`, `client_id`, `redirect_uri`
(`{origin}/api/auth/oidc/callback`; **the origin is the `PUBLIC_ORIGINS`
entry whose host equals the request's `Host`**, CR-08: a top-level GET
navigation carries no `Origin` header, so `share.link_origin`'s rule does
not apply; two entries with one host are refused by `POST`/`PATCH
/api/auth/providers` with a 409 naming the origins, and only **warned**
about at startup, R2-07: `check_startup` reads the environment before
migrations and must never refuse a start on database state, or a
`PUBLIC_ORIGINS` edit becomes a crash loop the recovery commands can't
reach; Settings lists one callback URL per origin),
`state`, `nonce`, `code_challenge`, `code_challenge_method=S256`. `next`
must match `^/(?![/\\])[\x21-\x7e]*$` and must not begin with `/api/`,
`/photos/`, or `/s/` (CR-15, R2-16: the `303` continues a cross-site
navigation, and a cookie request to `/api/` would be the gate's 403 as a
JSON page), else `/`; checked at start before it enters the flow cookie,
and every redirect is a `RedirectResponse`.
The start route runs the provider's discovery check first and answers
`/login?error=provider` if the provider can't be reached.

**Callback.** `GET /api/auth/oidc/callback?code=...&state=...`
(anonymous). In order: the flow cookie must be present and decrypt, `state`
must equal the cookie's (constant time), the cookie is cleared whatever
happens next (one use), `Sec-Fetch-Mode` if present must be `navigate` and
`Sec-Fetch-Dest` `document` (a fetch or an image can't complete a
sign-in), `error` from the provider is shown and audited (`access_denied`
is not a failure to throttle). The code is exchanged at the
`token_endpoint` (httpx, 10 s, the client secret in `Authorization: Basic`
or the body per the provider's advertised methods, `code_verifier`). The
ID token is verified: signature with `PyJWKClient` (the JWKS URI from
discovery; an unknown `kid` refetches once, at most once a minute), `alg`
in the allowed set (never `none`, never HMAC), `iss` equals the configured
issuer, `aud` is exactly the client id or a list holding it and no
untrusted others, and `azp`, whenever present, equals the client id
(CR-14, OIDC Core 1.0 section 3.1.3.7), `exp`/`iat`/`nbf` with 60 s leeway
and `exp`, `iat`, `iss`, `aud`, `sub` **required** (PyJWT checks a claim
only when present unless told to require it, CR-13), `nonce` equals the
cookie's, `sub` non-empty. PyJWT is called with `algorithms=` explicit,
`PyJWKClient(timeout=10, cooldown_duration=60, ssl_context=...)`, `oct`
keys refused, and pinned `>=2.14,<3` (CR-13). When discovery advertises
`authorization_response_iss_parameter_supported`, the callback's `iss`
parameter must equal the provider's issuer (RFC 9207; add list). **Nothing from the access token or userinfo decides the
identity**; `email` and `preferred_username` are read from the ID token
only for display. **The provider is the one in the flow cookie, never
one named in the request** (Q, mix-up): the callback carries no provider
parameter, and a code is only ever redeemed at the token endpoint of the
provider that the start route recorded, so a malicious provider's
callback cannot have its code redeemed elsewhere. Then:

- `intent=login`: look up `identities(provider_id, issuer, subject)`. Found
  and the user active: `accounts.start_external(...)` creates the session
  (rotating any session the browser held, as the password sign-in does),
  **sets the session cookie and, if absent, the browser cookie of item 6,
  never the device cookie** (CR-03, restated here where the builder reads
  it), audits `sign_in` with `detail.method: "oidc"`, computes the
  failed-since-last-visit count exactly as the password sign-in does and
  keeps it on the session for `GET /api/auth/me` to hand over once
  (R2-10: the notice is an A1 tripwire and a `303` has no body to carry
  it), sends the new-device alert when no valid browser cookie came with
  the request, and `303`s to `next`. Not found: no session, audit
  `sso_sign_in_rejected` with `reason: unlinked` (the `sub` is recorded,
  since it names nothing secret and the owner needs it to see who
  knocked), `303` to `/login?error=unlinked`.
- `intent=link`: the flow cookie's session-secret hash must be the current
  session's and the freshness recorded at start must hold; the identity
  must not already be linked; **`sub` must not look like an email or
  equal the token's `email` or `preferred_username` claim** (R2-06:
  Authentik's subject mode can put the email or username in `sub`, and an
  attacker who can set an unverified email at the provider would then
  receive the owner's `sub`; the refusal names the provider's subject-mode
  setting); then insert the `identities` row, audit and alert
  `identity_linked`, `303` to `/settings/signin?linked=<provider id>`.
  **Link outcomes never go to `/login?error=`** (R2-09): a signed-in app
  routes `/login` to `/` and drops the query, so an already-linked
  identity, a refused `sub`, or a provider failure `303`s to
  `/settings/signin?error=<code>`, and a confirm outcome `303`s to `next`
  with `confirm_error=<code>` when it failed, shown by the confirm
  dialog's host page; only `intent=login` uses `/login?error=`.

Failures a caller can cause (missing cookie, bad state, provider error,
token validation) redirect to `/login?error=<short code>` with the reason
in the audit row, never the token or the code. The callback (and
`POST /api/auth/trusted`) is throttled per address **in a bounded map of
its own**, keyed by IPv6 /64 like `throttle._shares`, with a global
per-minute cap, counting failures only (CR-09): a callback failure costs
an attacker nothing, and the shared map evicts oldest first, so failures
from many addresses would otherwise push out the admin's sign-in bucket
(the eviction v0.32.0 closed for share lookups). "One use" is enforced on
the server too (CR-17): a per-process set of consumed `state` hashes,
kept ten minutes, so a captured cookie and callback URL replay once at
most.

**How the gate lets it through (CR-01).** The start route is an ordinary
anonymous pair in `gate.ANONYMOUS` (its navigation from Settings or the
sign-in page is same-origin). The callback is different: it is by nature a
cross-site top-level navigation, and a `SameSite=Lax` session cookie
**rides along on it**, so today's layer 1 would look the session up, find
the request cross-site, and answer `403` before routing (`gate.py`,
`_lookup` returning `"cross-site"`): `link` and `confirm` could never
finish, and a login callback from a browser holding a live session would
fail too. The rule: **layer 1 passes `GET /api/auth/oidc/callback` with no
credential lookup at all**, principal `None`, like the share prefix, so no
`last_seen_at` moves and no CSRF decision is made for it; the handler
reads the session cookie itself through `sessions.find` without `touch`,
and for `link` and `confirm` requires the cookie's hash to equal the
session-secret hash the flow cookie recorded at start, the session to be
live, and (link) the freshness recorded at start. Nothing else in layer 1
changes. CSRF for the callback is the `state` bound to the flow cookie,
which a cross-site page can't read or set. The
callback **sets** a session cookie, so login CSRF is considered: an
attacker who starts a flow and hands the victim's browser the callback URL
fails on `state` (the victim's browser has no flow cookie, or one with a
different state). The start route redirects and reads no body; it is
reachable cross-site (a link from anywhere), which is fine: it only ever
sends the browser to the configured provider.

**Logs.** The code and state sit in the callback's query string.
`main._configure_logging`'s `uvicorn.access` filter (from v0.32.0) and
nginx's `map` both redact **any request target that begins with
`/api/auth/oidc/callback`, whatever follows** (a trailing slash, `HEAD`,
an `error_description`, CR-12 and Codex SSO-03), to
`/api/auth/oidc/callback?[redacted]`. A test through real nginx and the
uvicorn logger pins both. Known limit: nginx's `error_log` prints the
full request line on a 502 and has no format to redact; PKCE (a logged
code is useless without the verifier in the encrypted cookie) and the
server-side one-use state (CR-17) are the protection there.

**Discovery and keys** are cached in memory per process (discovery 24 h,
JWKS by PyJWT's own cache), fetched lazily on the first start, so
switching the provider on makes no request until someone signs in. A
provider that can't be reached at sign-in time is a 502 page
("The identity provider did not answer. Sign in with your password.").
Every outbound call has a 10 s timeout, follows no redirects, and sends
nothing but the protocol's own parameters (security.md's outbound list
gains the provider). **Trust for a homelab provider** (CR-11): a provider
behind a local certificate authority (which section 12 recommends) fails
verification in both httpx (which uses `certifi`, and `SSL_CERT_FILE`
would replace the public roots) and `PyJWKClient` (which fetches through
`urllib` with a different store). One optional `SSO_CA_FILE` is **added
to** the public roots and used by the httpx client and an explicit
`ssl_context` passed to `PyJWKClient`; deployment.md says the backend
must resolve and reach the issuer's browser-facing URL, since discovery
is `{issuer}/.well-known/...` and `iss` must match.

**Confirming a fresh action** (Q1) reuses the flow with `intent=confirm`
(which needs a live `oidc` session, not a fresh one: confirm exists for a
session that isn't fresh, CR-07), adding `prompt=login&max_age=0`; on
return `auth_time` must be present and within 120 s (a token without it
fails the confirm, never passes), **and the ID token's `(provider_id, iss,
sub)` must equal the identity the session signed in through**
(`sessions.identity_id`, CR-02): otherwise a stolen non-fresh session could
be confirmed by the attacker re-authenticating as their own user at a
provider with self-enrolment. A mismatch is `sso_sign_in_rejected`,
`reason: confirm_identity`, and the window stays shut. Then the session's
`confirmed_until` opens, `303` back to `next`. **Only where
the provider can do it** (Q11): the confirm dialog offers "Confirm at
<provider>" on an `oidc` session only when the provider's discovery
document lists `auth_time` in `claims_supported` and, if it publishes
`prompt_values_supported`, `login` among them (Authentik and Keycloak
do; Google lists neither, and Entra returns `auth_time` only as an
optional claim, so both fall back); `GET /api/auth/me`'s
`confirm_methods` carries that decision so the frontend needs no
provider knowledge. **An `oauth2_profile` provider never qualifies**
(R2-11): there is no ID token and no `prompt=login`, so `start` answers
403 to `intent=confirm` on such a provider and the callback refuses a
confirm with no verified ID token. The password is offered always, and is
the only method on a GitHub or trusted-header session; `FreshLink` learns
the same
choice.

## 5a. The `oauth2_profile` kind, and the GitHub preset

The same routes, flow cookie, `state`, PKCE, throttle, and audit rows as
section 5; what differs is after the code exchange. There is no ID token,
so `app/auth/oidc.py` asks the provider's **profile endpoint** with the
access token (`Authorization: Bearer`, `Accept: application/json`, 10 s,
no redirects) and reads the stable identifier from the JSON at the path
the preset names. The identity is `(issuer, subject)` with the preset's
fixed issuer string, so it lives in the same `identities` table and links
the same way. `nonce` is not sent (nothing would carry it back), which is
why `state` in the one-use cookie is the whole CSRF defence here as well.
A preset is data, not code:

| Preset | Authorize | Token | Profile | Subject | Display | Issuer string | Scopes |
|---|---|---|---|---|---|---|---|
| `github` | `https://github.com/login/oauth/authorize` | `https://github.com/login/oauth/access_token` | `https://api.github.com/user` | `id` (a number, stable for the account's life; `login` can change and is never used) | `login` | `https://github.com` | none (CR-16) |

Rules: the token response must be JSON (GitHub answers form-encoded
without the `Accept` header, which is the classic mistake) and carry
`access_token` with `token_type` equal to `bearer` **case-insensitively**
(RFC 6749 section 5.1, R2-12); the access token is used for
that one profile call and then dropped, never stored; a profile without
the subject field, or a non-numeric GitHub `id`, is a failure
(`sso_sign_in_rejected`, `reason: profile`). GitHub's OAuth app
registration needs the callback URL `{origin}/api/auth/oidc/callback`
(one per app; a second origin needs a second GitHub app). GitHub's
`email` is not requested: it is not needed for the identity and asks the
user for more than sign-in warrants; the scope is **empty** (CR-16: with
no scope, `GET /user` already returns the public profile with `id`, so
`read:user` was more than needed). The GitHub setup notes in
deployment.md say to turn on two-factor authentication at GitHub, or not
to link it: the button is only as safe as the GitHub account. A second
`oauth2_profile` preset
(Discord: `id`, `identify` scope) is a table row and a live check, not a
design change, and is not in v0.33.0 (Q9).

## 6. No second factor inside Cabinet

Decided on 24 September 2026 (Q2). The provider's MFA is the second
factor; Cabinet keeps only the password (Argon2id, the throttles, the
known-device cookie, the alerts) and adds `password_sign_in_alerts`.
`accounts.sign_in` sends `notify.send(db, "password_sign_in", ...)` on
every success when the switch is on, in addition to the new-device alert
(both may fire; the new-device one carries more, so the second is skipped
when the first was sent). Passkeys stay an optional roadmap item, with the
research notes in section 2.

## 7. The trusted-header mode

**Deployment contract.** Three environment variables on the backend, and
one of them on the proxy:

| Variable | Meaning |
|---|---|
| `TRUSTED_ASSERTION_HEADER` | The header carrying the gateway's signed JWT (`X-authentik-jwt`, `Cf-Access-Jwt-Assertion`, `X-Pomerium-Jwt-Assertion`, `X-Goog-IAP-JWT-Assertion`). Set on **both** backend and proxy; unset, the mode is off and nginx blanks every identity header as today |
| `TRUSTED_ASSERTION_JWKS_URL` | Where the gateway's public keys are; `https://` required, `http://` accepted only beside `AUTH_INSECURE_HTTP` (the local stack and CI) (Authentik: the provider's `jwks/` URL, also announced in `X-authentik-meta-jwks`; Cloudflare: `https://<team>.cloudflareaccess.com/cdn-cgi/access/certs`; Pomerium: `https://<authenticate>/.well-known/pomerium/jwks.json`; IAP: `https://www.gstatic.com/iap/verify/public_key-jwk`) |
| `TRUSTED_ASSERTION_ISSUER` and `TRUSTED_ASSERTION_AUDIENCE` | Required `iss` and `aud` (Authentik: the provider's issuer and client id; Cloudflare: the team domain and the application's AUD tag) |

`config.check_startup` refuses a partial set and an empty audience. The
header name is checked against `^[A-Za-z][A-Za-z0-9-]{1,60}$` and, in
both `check_startup` and the proxy's start script, **must not be any
header nginx sets or the gate reads** (R2-14): `Host`, `Cookie`,
`Authorization`, `Origin`, `Referer`, any `Sec-Fetch-*`,
`Content-Length`, `Content-Type`, `Transfer-Encoding`, `Connection`,
`Upgrade`, `X-Real-IP`, any `X-Forwarded-*`, `Forwarded`; otherwise
`TRUSTED_ASSERTION_HEADER=Host` would make the generated include pass the
client's raw `Host` over nginx's own.

**nginx.** `proxy/40-cabinet-hosts.sh` (renamed `40-cabinet-config.sh`)
writes `cabinet-identity.conf` at start: every identity header in a
**versioned list that includes every assertion header section 7 supports**
(today's blank list lacks `X-Goog-IAP-JWT-Assertion`, CR-18) set to `""`,
except the one `TRUSTED_ASSERTION_HEADER` names, written
as `proxy_set_header <Name> $http_<name_with_underscores>;`, and every
proxied location includes it (the list moves out of `cabinet-proxy.conf`
into the generated file; the proof is a rendered `nginx -T` plus a request
through real nginx in the smoke script, not a grep, since a location that
sets any `proxy_set_header` of its own drops the inherited ones).
So the assertion reaches the backend only when the deployment says so, and
nothing else ever does.

**Backend.** `GET /api/auth/state` reports `trusted_header: {available:
true}` from **deployment state only**: the four variables set and
`auth_config.trusted_header_enabled` true. It **never reads or verifies
the assertion** and carries no name from it (R2-03, Codex R2-02): every
anonymous boot request behind the gateway carries an assertion, PyJWT's
`PyJWKClient` fetches under a lock whose cooldown only starts after a
first successful fetch, and `auth_state` is a sync route holding a
threadpool thread, so a JWKS host that never answers (a wrong URL, an
untrusted local CA) would have stalled every sign-in page, exactly when
the password fallback is needed. Verification happens only on
`POST /api/auth/trusted` (anonymous, no body, `Sec-Fetch-Site` cross-site
refused, throttled per address in the CR-09 map, at most one JWKS fetch a
minute) and on the header link route: signature against
`TRUSTED_ASSERTION_JWKS_URL` with `PyJWKClient`, `iss`, `aud`, `exp`,
`nbf`, 60 s leeway, never `none` or HMAC; then the lookup of
`identities(kind='trusted_header', issuer, subject)`, and the session
(`auth_method: trusted_header`) or 403 `unlinked` with an audit row. A
verification that times out is a 502 with the fallback sentence, never a
wait longer than 10 s. Linking: "Link the identity this proxy asserts" in Settings
(admin, fresh) reads the current request's assertion and stores its
`(iss, sub)`. **A request's assertion never authenticates a route on its
own**: it is consulted only by `state`, `trusted`, and the link route, and
only to start a session. **Replay** (CR-05): a captured assertion works
until its `exp`, and for Authentik that is **the outpost session's
lifetime, not minutes**: the review read the outpost's source and found
`X-authentik-jwt` is the raw ID token the outpost obtained for its own
session, sent on every request, with the session's max age set from that
token's `exp`. Two deployment rules follow, in deployment.md (they are
about the network, so `check_startup` cannot check them; it checks only
the four variables): header mode is supported for Authentik **only with a
proxy provider dedicated to Cabinet** (a domain-level provider covering
several applications gives every co-hosted app an assertion with Cabinet's
`iss` and `aud`, and any of their logs or a compromised one yields a
working assertion) **with an asymmetric signing key selected** (an
unconfigured key means HS256 by client secret, which Cabinet refuses; the
mode then simply never sees a valid assertion); and with header mode on,
**the proxy port must be reachable only from the gateway** (Swarm: not
published; Compose: bound to the gateway's network), since the mode's
whole safety is that only the gateway can present the header.
`TRUSTED_ASSERTION_AUDIENCE` may not be empty. The JWKS URL comes only
from the variable, never from `X-authentik-meta-jwks`. The header only
ever travels gateway → nginx → backend, and the same holds for the session
cookie. The stage 3 build log records the live assertion's `alg`, `iss`,
`aud`, and `exp - iat` from the owner's Authentik, since none of this is
in Authentik's released documentation (not verified by the review, which
read the source on `main`).

**Why not `Remote-User` with a secret** is question 4.

## 8. Data model (`a0002`)

- `auth_providers`: `id`, `kind` (`oidc` | `oauth2_profile`, check),
  `preset` (`google` | `microsoft` | `github` | `custom`), `display_name`
  String(60), `enabled`, `issuer` String(255) (the OpenID Connect issuer,
  or the preset's fixed issuer string), `client_id` String(255),
  `client_secret` (Fernet text, write-only through the API), `scopes`
  String(255), `logout_at_provider`, `created_at`, `updated_at`; unique
  `(issuer, client_id)`. At most 8 rows. A `custom` row is `oidc`; the
  URLs of an `oauth2_profile` row come from the preset table in code, so
  the database never holds an authorize or profile URL a client chose.
- `identities`: `id`, `user_id` FK cascade, `kind` (`provider` |
  `trusted_header`, check), `provider_id` FK cascade nullable (set for
  `provider`), `issuer` String(255), `subject` String(255), `display`
  String(120) nullable (email or username at link time, for the Settings
  list only), `linked_at`, `last_used_at`; unique `(user_id, provider_id)`
  (one identity per provider), one `trusted_header` row per user (a
  partial unique index declaring both `postgresql_where` and
  `sqlite_where`, since tests build with `create_all`), unique
  `(provider_id, issuer, subject)` for provider identities and `(issuer,
  subject)` among `trusted_header` rows (CR-16: a global unique pair would
  stop one Authentik user, in global-issuer mode, being linked through
  both a provider and the header mode). Deleting a provider row deletes
  its identity, **after** its sessions are revoked (below).
- **`sessions.identity_id`** (CR-04, Codex SSO-02): nullable, FK to
  `identities.id` with `ON DELETE SET NULL`, set for every `oidc` and
  `trusted_header` session. It is what lets unlink, provider delete (all
  of that provider's identities), and `disable-sso` revoke exactly the
  matching live sessions **in the same transaction, before the delete**,
  and what the confirm identity check (CR-02) compares against. A provider
  delete never touches `trusted_header` sessions. Without it a session's
  source is only `auth_method`, and Q12 could not be implemented per
  provider.
- `auth_config` (singleton, `id = 1` check): `password_sign_in_alerts`,
  `trusted_header_enabled` (default true, R2-02), `updated_at`. Read with
  the provider rows through `app/auth/config.py` **from the database on
  every use, never cached** (R2-01): the container commands write from
  another process, and a cache would keep a disabled provider's button
  alive until a restart.
- `known_browsers` (R2-04): `id`, `user_id` FK cascade, `secret_hash`
  bytes(32) unique, `created_at`, `last_seen_at`, `expires_at`; the alert
  cookie's rows, pruned hourly with the rest.
- **Constraints** (R2-13, R2-15): `auth_providers` has
  `(preset = 'github') = (kind = 'oauth2_profile')` as a check, and the
  `github` and `google` issuers are fixed in code; `issuer`, `client_id`,
  `kind`, and `preset` cannot change on a provider that has a linked
  identity (`PATCH` answers 409: delete and re-add), so a linked provider
  can't be repointed under its identity. `identities` has
  `(kind = 'provider') = (provider_id IS NOT NULL)`; a session with
  `auth_method` `oidc` or `trusted_header` and no `identity_id` is refused
  by confirm. `password_sign_in_alerts` is set true, audited, when a
  provider is enabled while none was (R2-17, decision 10), and never
  changed automatically again. `tests/test_auth_schema.py` is updated for
  `a0002` (every version file read, the new table set, head `a0002`), and
  its "never mention `public`" grep is scoped to the word as a schema name
  so a comment about a public client doesn't trip it.
- Drop `users.external_issuer` and `users.external_subject` (Q5).
- `sessions.auth_method` already fits the three values; `identity_id`
  is the one new session column.
- Nothing in `public` changes: **no collection migration** in v0.33.0.

## 9. The gate, layer by layer

Layer 1 gains these anonymous pairs: `GET /api/auth/oidc/start`,
`GET /api/auth/oidc/callback`, `POST /api/auth/trusted`. The POST joins
`SMALL_BODY`. No other gate rule changes: the maintenance
rule, the share prefix, the token rules, and CSRF for cookie requests stay
as they are, except that the callback passes with no lookup (section 5,
CR-01). Layer 2: every new route declares its class (table below), and
**the rows go into SPEC_0300's appendix** under "Single sign-on routes
(v0.33.0)", as P9's did (CR-19: `test_gate.py` splits SPEC_0300 on its
appendix heading and pins the operation count, so a second file would
need a second parser for nothing). `test_gate.ANONYMOUS` grows by the
three pairs; the encoding, scope, fresh, and CSRF matrices run over the
new routes for free, and the callback gains a test of its own: a live
session cookie with `Sec-Fetch-Site: cross-site` reaches the handler with
principal `None` and moves no `last_seen_at`.

**New routes**

| Method | Path | Class | Note |
|---|---|---|---|
| GET | `/api/auth/oidc/start` | public | `provider=<id>`; 302 to that provider; sets the flow cookie; 404 for an unknown or disabled provider; `intent=link` needs a fresh session, `intent=confirm` a live `oidc` session whose provider qualifies (403 otherwise, CR-07) |
| GET | `/api/auth/oidc/callback` | public | Layer 1 passes it with no credential lookup (CR-01); 303 to `next` or `/login?error=`; one-use flow cookie and state; throttled on failure in its own map |
| POST | `/api/auth/trusted` | public | Verifies the assertion (the only anonymous route that does, R2-03) and starts a session; 404 when the mode is off or switched off (R2-02); 403 unlinked; 8 KiB; throttled |
| GET | `/api/auth/signin-config` | admin | The providers (secrets masked), the linked identities, the alert switch, and the preset list |
| PUT | `/api/auth/signin-config` | admin, fresh | Change the alert switch or switch the trusted-header mode back on (R2-02); audited (`sso_configured`) |
| POST | `/api/auth/providers` | admin, fresh | Add a provider from a preset or a custom issuer; `dry_run` fetches discovery only; audited (`sso_configured`), alerted |
| PATCH | `/api/auth/providers/{id}` | admin, fresh | Change it (a secret is replaced, never read back; `issuer`, `client_id`, `kind`, `preset` are 409 while an identity is linked, R2-13); audited, alerted |
| DELETE | `/api/auth/providers/{id}` | admin, fresh | Remove it and its linked identity; audited, alerted |
| DELETE | `/api/auth/identities/{id}` | admin, fresh | Unlink; audited, alerted |
| POST | `/api/auth/identities/trusted_header` | admin, fresh | Link the current request's assertion |

**Changed routes**: `GET /api/auth/state` adds `methods: {password: true,
providers: [{id, name, preset}], trusted_header: {available} | null}`
(no name, R2-03); `GET /api/auth/me` adds `auth_method`,
`confirm_methods`, and, once per session, `failed_since_previous` and
`previous_sign_in_at` (R2-10); `POST /api/auth/logout` on an `oidc`
session with logout-at-provider on answers `{"redirect": <end_session
URL>}` for the frontend to follow.

## 12. Docs

deployment.md gains a section of its own, **"Exposure: Cabinet is for
private networks"**, near the top and linked from the README's quick
start, from `.env.example`, and from Settings → Sign-in. It is a hard
recommendation, the owner's decision of 24 September 2026 (reversible
later, but this is the position now), stated plainly and at length:

- **Cabinet is intended for private use on private networks. Do not
  expose it to the internet.** Not behind TLS, not behind single sign-on,
  not behind an authenticating gateway: none of those changes the
  recommendation. No port forward, no public DNS name pointing at it, no
  "just for a while".
- **To reach it from outside the network, use the network's own remote
  access**: a VPN (WireGuard, Tailscale, the router's own) or an
  identity-aware tunnel that terminates before Cabinet, so that Cabinet
  itself is never reachable from the internet. That is how the owner's
  own deployment works.
- **Why.** Cabinet has one admin account and, by design, a password path
  with one factor so that a provider outage or a lost phone can never
  lock the owner out; single sign-on adds the provider's MFA to the
  provider's button, not to that password. The sign-in is hardened
  (Argon2id, throttles, the known-device cookie, alerts on new devices,
  `Secure` cookies, the CSRF check), but one guessed or leaked password on
  an internet-facing instance is the whole collection, its storage
  locations, and its documents. Cabinet cannot make a guessed password
  fail; a private network makes the guess impossible to attempt.
- **What still applies inside the network**: TLS from a local certificate
  authority or the reverse proxy, a long random password in a password
  manager, the alert webhook and `password_sign_in_alerts` on, and single
  sign-on with MFA for everyday use so the password is rarely typed.
- **Share links are for your network too** (Q17). Someone opens a share
  link from inside the network or over your VPN; a share link is not a
  reason to expose Cabinet, and exposing only the share paths through a
  gateway path rule is not a recipe the project stands behind (one path
  too many and the sign-in page is on the internet). The forward-auth
  exemption in section 3 is for a gateway inside the network.
- **If you ignore this** the document does not offer a "safe" recipe,
  since there is none the project stands behind; it says only that the
  owner of such a deployment carries the risk, and that the least that
  should be true is TLS, single sign-on with MFA enforced at the
  provider, an authenticating gateway in front, the alert switch on, and
  a password no human has memorised.
- **The standard warning, verbatim wherever exposure comes up.** One
  block of text, kept in deployment.md and repeated (not paraphrased or
  shortened) in security.md, README, `.env.example`, the sharing section
  of deployment.md, and the Settings → Sign-in and Sharing pages' help
  text: that Cabinet is designed for private networks; that exposing it,
  or any self-hosted service holding personal records, to the internet
  invites automated credential guessing, vulnerability scanning, and
  exploitation of any future defect within hours of the port opening;
  that the project cannot see or control how it is deployed and takes no
  responsibility for an exposed instance; that the recommendation is a
  VPN or identity-aware tunnel; and, for anyone who exposes it anyway,
  the least-that-should-be-true list above. The owner's rule, 24
  September 2026: the project educates through recommendations and
  warnings; it does not police deployments.

## 14. Risks and open items

- **The callback is the first cross-site navigation that sets a session
  cookie.** Its safety rests on the `state` in an encrypted, one-use,
  path-scoped cookie and on refusing anything that isn't a top-level
  navigation. The review should read `oidc.callback` first.
- **A provider that publishes HMAC or `none` algorithms** is ignored: the
  allowed set is fixed in code.
- **Clock skew** at the homelab: 60 s leeway; a further-off clock fails
  with a clear message naming the skew.
- **The password path is one factor** (Q2), by the owner's decision. The
  mitigation is documentation (section 12), the alert switch, and A1's
  throttles; the review should say whether it agrees that is enough for
  the stated deployment (a private network, or SSO with MFA in front).
- **Numista confirmation and the other v1.0.0 items** are unaffected;
  v0.33.0 adds no collection migration.
