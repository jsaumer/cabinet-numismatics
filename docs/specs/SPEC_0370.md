# SPEC_0370: Cabinet v0.37.0, proof and mint sets

Status: **approved by the owner on 25 October 2026**, to be built stage by
stage on `mint-sets` (section "Stages"). Asked for on 20 October 2026:
one item for an official proof, uncirculated, or specimen set, as issued by
a mint. Nothing is open: the price-source probe (stage 0) is done for both
sources (build log), and everything else reflects the owner's answers of 20
and 25 October 2026, including the comparison with other tools and the
packaging fields.

## Why

A proof or mint set is bought, kept, and sold as one thing, often sealed,
and priced as one thing (Greysheet, the PCGS price guide, eBay, and auction
records all list whole sets). Cabinet has no way to say so. Entering each
coin and grouping them in a Set (`ItemSet`, name and notes only) splits one
purchase price across coins by hand and gives the set no value of its own;
entering the set as a Coin counts it as one coin, asks for a grade and a
mint mark it doesn't have, and can't value its silver.

## What the research found

**How other tools handle sets** (checked 20 October 2026):

| | Numista | PCGS | CoinManage | Greysheet |
| --- | --- | --- | --- | --- |
| A set is one record | yes, its own number (`N#S2077`) | yes, a price guide section | yes, a database entry | yes, one price row |
| Official issues only | yes ("official packaging from the mint") | US Mint | US, Canada, UK mint products | US issues |
| What a set records | issuer, mint, year, Krause reference, contents | year, variant, grade | catalog fields | year, variant |
| The coins inside, listed | yes, each linked to its coin page | no | no | no |
| Packaging | no | no | no | "critical" to value, in prose |
| Value | the owner's purchase price, not split across the coins | guide price by proof grade (PR) | built-in values | dealer bid and ask |

- **Numista launched sets in 2025** (forum topic 108347, marked
  implemented). A set page, such as the 1981 San Marino Mint Set
  (`N#S2077`, Krause `MS18`), carries the issuer, mint, year, references,
  and a contents list linking each coin and its issue; a member can add a
  set to their collection with a purchase price. The website gained a set
  search (by issuer and year) in July 2026, and a set page such as the
  1981 United States Proof Set Type 1 (`N#S162`) also shows the issued
  quantity, the issue price, and each coin's Numista and PCGS numbers.
  Members' main complaint was counting twice: a
  set's price isn't spread across its coins, and recording both the set
  and its coins counts the coins twice. The search fields Numista's team
  floated (country, year, proof or uncirculated, number of items) are the
  fields this spec gives a set. **The API does not return sets** (stage 0,
  build log), and **Numista's Terms of Use forbid reading the website
  instead** ("reproduction, extraction or reuse, by any means, including
  methods similar to scrapping"), so Cabinet only ever reaches Numista
  through its API, as today: the owner reads a set page and types what
  Cabinet holds, and Cabinet links to the page, never fetches it.
- **PCGS numbers whole sets**: its price guide has a "US Proof & Mint Sets"
  section, "Proof Sets (1936 to Date)", priced by proof grade on the
  website. Its API knows a set by PCGS number but gives it no guide price,
  no graded population (PCGS grades a set's coins, not the set), and only
  old ungraded auction lots (stage 0, build log), so Cabinet can't price a
  set from it.
- **CoinManage** lists "all USA coins, sets and mint products" in its
  database, cross-referenced to PCGS numbers: one record per set, valued,
  is normal in desktop software too.
- **Greysheet** gives each year and variant its own row (95 for US mint
  sets since 1947; a 1936 proof set in satin finish is its own), and says
  the condition of the original packaging is critical to value.
- **Krause** numbers proof sets `PS` and mint sets `MS`, so the existing
  free-text catalog references hold them, as Numista's pages do.
- **A new type value needs no column change**: `items.type` is
  `Enum(..., native_enum=False, length=10)`, so `mint_set` (8 characters)
  fits, as `bullion` did in SPEC_0310.
- **The sales log already copes with no grade**: `comps.item_bucket`
  returns `None`, every logged sale then matches, and the confidence loses
  0.05 for "no grade to hold the sales against".
- **Year checklists can already track sets**: generated by year range and
  matched on country plus denomination, so "US Proof Sets 1950 to 2025"
  works once set names are consistent.

**Where this plan stands against them**: ahead on packaging (no tool
records it as data), melt and an optional place in the stack, a sales log
with an explained value, and specimen sets as a kind of their own; behind
Numista on the contents list (below, out of scope); level with Numista on
counting twice, which the docs and the form address (section 1).

Options weighed: A, a Coin by convention (counts as a coin, no packaging,
no melt); **B, a fourth type (chosen)**; C, a set with a structured list of
its coins, as Numista has (melt and per-coin checklist matching from the
contents; much larger, and can be added on top of B later).

## Scope

**In scope**

1. **A fourth item type, `mint_set`**, shown as **"Proof or mint set"**
   (the list filter reads "Proof and mint sets"). Official issues only.
   - **What counts as a set**: a proof, uncirculated, or specimen set
     issued and packaged by a mint. Themed sets (baby, wedding, birthday,
     gift, Prestige, Premier) are the kind they are, with the theme in the
     name. A dealer-assembled set is entered as its coins, grouped with
     Sets. A mint-wrapped roll is one coin item with its quantity; a coin
     card is one coin item. The form's help text and the docs say so.
   - **Two kinds of set named outright** (the owner's choice, 25 October
     2026), so neither is mistaken for something else:
     - **Coin and currency sets**, which a mint sells with a banknote
       beside the coins (the US Mint's sets pair a Bureau of Engraving and
       Printing note with coins). They are a set of this type, named as a
       variant ("Coin and Currency Set"); the note counts in `piece_count`,
       and its serial number goes in the notes, since the note fields are
       hidden for a set. Entering the note as its own item as well counts
       it twice, the same rule as for coins.
     - **Bullion proof and uncirculated sets**, such as a four-coin
       American Gold Eagle proof set. They are a set of this type, not
       bullion: the precious metal in the whole set gives melt, and
       ticking the stack checkbox (section 3) counts their ounces. This is
       where that checkbox matters most, and the form's help text uses one
       as its example.
   - **Kind** is the existing `strike`: `proof` is a **Proof set**,
     `business` an **Uncirculated set**, `specimen` a **Specimen set**. A
     new set defaults to Proof. There is no fourth kind.
   - **Issuing mint** is the existing `issuer`, holding the issuing
     authority ("United States Mint", "Royal Canadian Mint", "Royal Mint"),
     never the facility that struck it: Numista's set pages name the
     facility ("United States Mint of San Francisco"), which has no single
     answer for a US mint set struck at Philadelphia and Denver, so the
     facility, if wanted, goes in the notes (the owner's choice, 20 October
     2026). The form's placeholder and help text say so. It is what makes
     the set official. **Required
     on the form, accepted empty by the API** (the owner's choice, 20
     October 2026), so an import can land a set when its source doesn't
     carry the mint (Numista's export doesn't); the data-health widget
     counts sets still missing one (section 7).
   - **Year** is required; there is no ND for a set (`year_nd` must be
     false). A set holding coins of several dates takes its year of issue.
   - **Set name** is the existing `denomination`, without the year:
     "Proof Set", "Silver Proof Set", "Prestige Proof Set", "Special Mint
     Set", "Baby Set". The form suggests one from the kind and the metal
     ("Proof Set", "Silver Proof Set", "Uncirculated Set", "Specimen Set")
     until the owner types their own, the `autoYear` pattern. Named
     variants (Special Mint Set, Prestige, Premier, Limited Edition, and
     the themed sets) are typed as the name, never a fourth kind.
   - **Set names stay consistent**: the name box offers every set name
     already used (a datalist, as Country has, built from
     `GET /api/items?type=mint_set`, so no new route), because a year
     checklist matches a set by country plus name, and "Proof Set" one
     year and "Proof set" the next would break the run. The owner settles
     the convention with the first few sets ("Proof Set", "Silver Proof
     Set", "Prestige Proof Set", "Special Mint Set").
   - **Label**: year, then issuer or country, then the set name: "2023
     United States Mint Proof Set", the shape Numista's titles take.
     `routers/items._name_key` gains the same case, so Piece A to Z sorts
     sets by year among the coins and notes.
   - **New fields** (migration `0023`), shown only for this type:
     `piece_count` (every piece in the set: coins, any banknote, and any
     mint token or medal, 1 to 100) and the three packaging fields (section 2).
   - **Reused**: country, series ("America the Beautiful"), variety (an
     error set, such as a missing mint mark), mintage shown as **"Sets
     issued"**, catalog references, notes, photos, documents, tags, Sets,
     every acquisition, storage, and sale field. The item page's mintage fact
     (`components/item-facts.tsx`, offered to coins and notes today) is
     offered to sets too, labeled "Sets issued", as "Print run" is for a
     note.
   - **The mint's issue price** (Numista's "Issued Price $11.00") goes in
     the notes; there is no field for it (the owner's choice).
   - **Hidden for this type**: grade and its parts (plus, star,
     designations, details, CAC), since nothing grades a set as a unit
     (section 4); cert and population; mint mark, die axis, the date as struck, the
     physical fields (diameter, size, thickness, edge, shape), and the note
     and bullion fields (serial, signatures, prefix, printer, watermark,
     charter). Fancy serial traits are never computed for it, as for
     bullion.
   - **Counting twice**: the form and the docs say to enter a set either
     as one set item or as its coins, never both, or its coins count twice
     (the complaint Numista's members raised). Nothing enforces it.
   - **Counts**: `counts.mint_sets` on `/api/stats/collection`; `coins`,
     `notes`, and `bullion` keep their meaning, so the Homepage tile keeps
     working. The type breakdown and `cabinet_items{type}` gain the value;
     the value hero adds "· 6 proof and mint sets" when non-zero.
2. **Packaging** (option B, the owner's choice on 20 October 2026), three
   nullable columns in migration `0023`:
   - `packaging` (`String(12)`): `sealed` (never opened), `complete`
     (opened, every piece in the mint's holder), or `incomplete` (a piece
     missing or replaced); empty means not recorded. Shown as a select:
     Sealed, Complete, Incomplete.
   - `has_box`: the mint's outer box or sleeve is present (a checkbox).
   - `has_coa`: the certificate of authenticity is present (a checkbox).
   - Holder condition (a cracked lens, haze, toning) goes in the notes.
   - The list filters on `packaging=` (the three values); the item page
     shows "Sealed, with box and certificate" or "Complete, no
     certificate" in one line; bulk edit leaves them alone (they describe
     one set, not a batch).
   - Considered and passed over: a single three-way choice (can't record
     a missing certificate, which costs a modern US set real money) and
     free text in the notes (can't be filtered or sorted).
3. **Precious metal and the stack.**
   - A set's composition, weight, and fineness mean **the precious metal in
     the whole set**, labeled "Precious metal in the set". The form offers
     the bullion Metal select (none, silver, gold, platinum, palladium);
     weight is the total weight of the precious coins, with the g / oz
     switch. Melt then works unchanged ("2023 Silver Proof Set", 5 coins of
     .999 silver).
   - **A set counts in the stack only when the owner says so**: a new
     column `count_in_stack` (boolean, default false), a checkbox on the
     form shown when a precious metal, weight, and fineness are given, and
     bulk-editable. This reads the owner's two answers together ("count
     them in the stack" and "no, but optional"): sets can count, off by
     default. Melt is a value and applies either way; the stack, the
     purchase-day spot backfill (`stack.needs_spot`), the
     `cabinet_stack_fine_ounces` gauge, and the `stack` widget leave a set
     out unless it is ticked. One function, `stack.counts(item)`, decides
     it for all of them, so the rule that `fine_oz`, the stack, and melt
     agree on what is bullion gains this one stated exception. Coins, notes,
     and bars are unchanged (the column is ignored for them).
4. **Valuing a set.**
   - Typed values and the sales log work today; for this type the sales
     log's "no grade" confidence penalty is waived, since a set has no
     grade by design.
   - **PCGS and Numista refuse a set** with a clear reason in their
     `prerequisite` ("PCGS doesn't price sets in Cabinet", "Numista doesn't
     price sets in Cabinet"), so pricing coverage explains it. Stage 0
     showed neither can (build log): Numista's API has no sets, and PCGS's
     answers a set with no guide price and auction lots too old for
     Cabinet's five-year window. If either changes, wiring it in is a
     release of its own.
   - **No grade on a set.** The optional grade this spec held open for
     PCGS is dropped: PCGS reports a graded population of 0 for a set at
     every grade asked (it slabs the coins, not the set), so a set-level
     grade would have nothing behind it. A set's coins graded and slabbed
     on their own are entered as coins.
5. **Catalog references and lookups.**
   - A Numista set number is a catalog reference like any other, written
     `numista_set` with its code (`S2077`); the item page's "Look it up"
     links (`components/lookup.tsx`) gain **Numista set** opening
     `https://en.numista.com/S<number>`. A link only, no request; it works
     before and whatever the probe finds.
   - Krause `PS` and `MS` numbers go in as `km` references, as today.
   - A **PCGS set number** goes in as a `pcgs` reference (904795 for the
     1981-S Proof Set Type 1), and the item page's CoinFacts link, today
     offered for coins only, is offered for a set too
     (`https://www.pcgs.com/coinfacts/coin/detail/<number>`). A link only;
     PCGS still refuses to price a set (section 4).
6. **The list and entry.**
   - The Add form's type choice gains "Proof or mint set";
     `/items/new?type=mint_set` presets it. Quick add stays coins, notes,
     and bars (its lookups can't fill a set yet).
   - The type filter and bulk edit gain it.
   - **One place per type, first** (a refactor at the start of stage 1,
     with no visible change): the item page's hero, the share grid, and the
     share piece page each pick a type's icon with a coin-or-bullion-else-note
     check, so as written a set would show a banknote's icon. One
     `typeIcon(type)` and one table of type labels (the form's choice, the
     list filter, the breakdown, the value hero) replace those checks, so
     this type, and any later one, is one entry; TypeScript's exhaustiveness
     check on that table catches a place left out.
   - The workbench list's type mark gains a fourth shape (a case holding
     coins), colored by the set's metal like the others, and `typeIcon`
     draws the same case on the item page and on share pages.
   - **The list's Grade column shows a set's packaging** ("Sealed",
     "Complete", "Incomplete") where a coin shows its grade, and an en dash
     when none is recorded; the Grade heading's sort leaves sets at the
     end, as it does ungraded pieces.
   - **The Numista fill card is hidden for a set**: the API has no sets
     (stage 0), and a coin search would only mislead. The Numista set
     number is typed as a reference instead (section 5).
   - The item page groups the set's facts: the set (kind, issuing mint,
     pieces, sets issued, packaging), precious metal (when given), then the
     usual acquisition and storage groups.
7. **Imports, exports, sharing.**
   - The Cabinet CSV and XLSX gain `piece_count`, `count_in_stack`, and the
     packaging columns and round-trip them; an older export still imports.
   - A spreadsheet Type cell reading `proof set`, `mint set`, `uncirculated
     set`, or `specimen set` maps to `mint_set` with the matching kind.
   - The share view's allowlist gains `piece_count` and the packaging
     fields (descriptive, like composition); `count_in_stack` stays out.
     The allowlist test changes in the same commit.
   - **The data-health widget** (`insights.data_health`) gains a check, sets
     with no issuing mint, and its "no grade" check skips sets (a set has
     no grade by design).
   - **The grade figures leave sets out**: `insights.quality_stats` (the
     certified share widget's certified, raw, graded, and ungraded counts
     and values) skips sets, which can't be certified as a unit, so adding
     ten sets doesn't lower the certified percentage. The grade breakdown
     already leaves out a piece with no grade.
   - **The insurance report and the printable report** print a set's
     packaging in one line ("Sealed, with box and certificate") where a
     coin prints its grade and cert, since a missing box or certificate
     changes what an insurer pays; pieces and sets issued go with it.
8. **Sets from Numista's collection export.** The export (seen 20 October
   2026, build log) lists a set as its coins, one row each, with the set's
   title in a `From set` column (empty for a loose coin) and, since August
   2026, the set's buying price on one row only. Today the importer ignores
   `From set`, so a set arrives as loose coins, each a business strike
   graded at the bottom of uncirculated (Numista grades proofs "UNC"), and
   a set's price lands on one coin. The import preview now groups rows by
   their `From set` value (never by position: the export sorts by
   denomination, so a loose coin can sit between a set's rows) and imports
   each group as **one Proof or mint set**, the owner's choice:
   - **Kind** from the title: "Proof" is a Proof set, "Specimen" a Specimen
     set, anything else an Uncirculated set.
   - **Year** from the title's leading four digits, else the year most of
     the rows share; **set name** is the title less that year and the
     issuer ("Proof Set Type 1"); **country** from the rows' Issuer.
   - **Pieces** is the number of rows in the group; the set's own quantity
     is the smallest Quantity among them, so two copies of a set exported
     as rows of 2 import as one set item of quantity 2.
   - **Buying price** is the sum of the group's buying prices, right
     whichever row Numista put it on; the currency is the column's.
   - **Contents in the notes**: "Contents: N#42 1981 S, N#44 1981 S, …",
     ready for the coins-inside-a-set feature later, with the rows'
     comments after it.
   - **Left for the owner**, and said in the preview: the issuing mint and
     the Numista set number (the export carries neither; the set's title
     is kept in the preview line so it can be found on numista.com), and
     the precious metal (the export has no composition column).
   - The per-coin grades and Numista's per-coin estimates aren't carried
     over to the set.
   - **The import key** is the set's title plus the sorted list of its
     rows' keys, so importing the same export again skips the set as a
     duplicate, as it does a coin.
   - **Importing as its coins** stays a choice per group in the preview,
     for a set the owner has broken up: the coins come in as today, but
     marked proof when the set's title says Proof, and each with a note
     naming the set.
   - The Numista account import (the API) has no sets to group: the API
     doesn't expose them (build log), so it is unchanged.
9. **The demo collection** gains one proof set with a public domain photo,
   if Wikimedia Commons has a suitable one (checked before stage 5 starts;
   without one, the demo set goes in without a photo, never with a photo
   whose license isn't public domain or CC0).

**Out of scope:**
- **The coins inside a set** (option C). Numista links a set's contents,
  so there owning a 1964 proof set fills the 1964 Kennedy half in a date
  run; in Cabinet it won't, and the docs say so. A later release can add
  contents on top of this type, filled from Numista when its API allows.
- Mint-wrapped rolls and coin cards (entered as coins; see section 1).
  If their packaging needs recording, the way in is to let coins carry the
  packaging fields, not to widen this type.
- Dealer-assembled sets, a Numista fill for sets until the API returns
  them, quick add for sets, and OpenNumismat import of sets.

keeps the new type value out of the stability promise's first version.

## The owner's answers (20 October 2026)

- One item per official set (mint-issued only): proof, uncirculated, and
  specimen sets.
- Sets can count in the bullion stack, **optionally, off by default**.
- Special Mint Sets, Prestige, Premier, and themed sets are **named
  variants** (the set name), not a fourth kind.
- **No fourth kind for other mint packaging**: rolls and coin cards are
  entered as coins.
- **Coin and currency sets and bullion proof sets are sets** (25 October
  2026): named in section 1, the first with its banknote counted as a piece,
  the second counted in the stack when ticked.
- After the comparison with other tools: a Numista set number as a catalog
  reference with a lookup link, a probe pointed at a real set, an optional
  grade only if PCGS prices sets, and a note on counting twice, all folded
  in.
- **Packaging is option B**: Sealed / Complete / Incomplete, plus box and
  certificate checkboxes.
- **Sets in Numista's export import as one Proof or mint set** by default,
  with importing as coins kept as a per-set choice.
- **Issuing mint**: required on the form, accepted empty from an import or
  the API, and counted by the data-health widget. It holds the authority
  ("United States Mint"), not the striking facility Numista names.
- **The issue price** goes in the notes, not a field of its own.
- **No grade on a set, and no PCGS or Numista pricing** (25 October 2026,
  after the probe): a PCGS set number is a reference with a CoinFacts link.
- **The gaps found by walking the code are folded in** (25 October 2026):
  one place per type (icons and labels), "Sets issued" on the item page,
  sets left out of the grade figures, no Numista fill card for a set,
  set-name suggestions for consistent checklists, packaging in the list's
  Grade column and in the reports, PR #69 first, and a live check with the
  real export.
