# Codex adversarial review, round 3: encrypted archives and proxy gateways

Reviewed at commit 25387bc.

## Verdict

**Not safe as written.** The updated age plus key-derived MAC design is
appropriate, including MAC coverage of the canonical manifest and
SHA256SUMS, but the planned decrypt staging location is inside BACKUP_DIR,
which can recreate a plaintext collection on the share that encryption is
meant to protect. This is a structural staging-boundary change; the rotation,
legacy, rollback, and mount-topology items below are precise contract and
documentation rules.

## Findings

| ID | Severity | Harm enabled | Attack | Evidence | Exact contract rule | Test that proves it |
| --- | --- | --- | --- | --- | --- | --- |
| B1 | critical | Knowing what is where and its value; personal data | A backup-share reader cannot decrypt an age file at rest, but an owner who inspects or restores it causes Cabinet to write the decrypted zip into .restore-staging on that same share. The reader can copy the plaintext zip while it exists, recovering items, locations, photos, and receipts without the backup key. A naive adaptation of current download and partial-file paths has the same failure mode. | The contract says inspect decrypts into .restore-staging (docs/specs/SPEC_0300.md:177). Current staging is under backup.backup_dir() (backend/app/services/restore.py:112-115), and the security document still says uploads stream into BACKUP_DIR/.restore-staging (docs/security.md:381-384). Current download and safety-backup temporary zip files are placed in the backup directory (backend/app/services/backup.py:270-282, backend/app/services/backup.py:316-328). | Add a required, capacity-checked private RESTORE_STAGING_DIR, separate from BACKUP_DIR and the photo directory. Decrypt only there, with restrictive permissions; delete it on every success and failure path. No plaintext archive, member, partial, or download file may ever be created in BACKUP_DIR. Archive creation must stream the zip into age, and restore.sh must use a private mktemp directory with a cleanup trap rather than a file beside the archive. | A filesystem watcher on BACKUP_DIR observes only age ciphertext throughout download, scheduled, safety, inspect, successful restore, failed decrypt, and interrupted restore. The decrypted zip exists only under RESTORE_STAGING_DIR, has mode 0600, and is removed after each path. |
| B2 | high | Availability | Key rotation has no defined MAC-key selection. An archive encrypted under the old identity must remain readable while that identity is retained, but the contract does not say whether verification derives its MAC key from the active first identity, every identity, or the identity that decrypted it. A first-key implementation makes all old archives fail after rotation; an unspecified all-key implementation is fragile and leaves no stable audit explanation. | Multiple identities are permitted, the first encrypts, and all are tried to decrypt (docs/specs/SPEC_0300.md:167); rotation retains old identities (docs/specs/SPEC_0300.md:174); but the MAC is derived only from "the identity" (docs/specs/SPEC_0300.md:169). The updated MAC coverage resolves the prior manifest-substitution concern, but does not choose the MAC identity. The [age v1 specification](https://age-encryption.org/v1), checked directly, defines an X25519 identity as 32 random bytes encoded in Bech32, so use of the decoded raw identity is sound but does not make Cabinet's selector unambiguous. | Add mac_recipient to the MAC-covered manifest: the exact age public recipient derived from the identity that made the archive. On restore, parse only enough to select one configured identity whose derived recipient equals mac_recipient, derive that identity's HKDF key, and require its constant-time MAC comparison to pass. Reject an unknown or duplicate recipient. A Docker-secret rotation must explicitly supply new then old identities; backup-key rotate only writes a generated, writable key file. | Make archive A with the old key, rotate to new plus old, then restore A and make archive B. A and B both restore while both keys exist; A fails once old is removed; changing only mac_recipient fails; a read-only BACKUP_KEY_FILE makes the CLI print the documented external rotation steps without trying to modify it. |
| B3 | medium | Control of the collection record | A backup-share writer can replace a current authentic archive with an older authentic archive. Its age and MAC checks pass, but restoring it rolls the collection back, potentially removing recent entries, documents, or valuation history. The owner may see its date, but the design does not compare it against a Cabinet-held monotonic record. | The archive specification defines no backup generation or accepted-generation state (docs/specs/SPEC_0300.md:165-183). Credentials and their schema survive restores (docs/specs/SPEC_0300.md:88-105), so cabinet_auth can retain rollback knowledge safely. | Store a monotonically increasing, MAC-covered backup generation and the newest accepted generation in cabinet_auth. Inspection of a lower generation must display a persistent rollback warning and require a distinct typed confirmation such as RESTORE ROLLBACK; it must audit and alert. A new machine with no retained state may restore normally but must say rollback detection is unavailable. | Generate two archives, replace the later with the earlier, and inspect it. The UI reports rollback and run rejects ordinary RESTORE; the explicit rollback path records the generation. A newer generation has no warning. |
| B4 | medium | Control of the collection record | The in-app RESTORE UNENCRYPTED exception permits a backup-share writer with no key to manufacture a plausible legacy zip, recompute its internal checksums, and wait for the owner to restore it. A typed phrase proves intent, not archive origin, so it contradicts the claim that a share writer cannot make an archive that restores. | Legacy plain archives remain restorable in-app after a typed phrase (docs/specs/SPEC_0300.md:172), while the planned security statement says a share writer cannot make an archive that restores (docs/security.md:341-346). Current verification trusts a manifest and member checksums from the archive itself (backend/app/services/backup.py:214-235; backend/app/services/restore.py:232-259). | Do not offer legacy unencrypted restore in the web UI. Provide a documented, host-only migration command that seals a deliberately chosen legacy zip into a MAC-authenticated age file, with a conspicuous warning that pre-sealing origin cannot be proved. The normal in-app restore accepts only encrypted, authenticated archives. | A valid plain legacy zip is absent from in-app restore choices and upload rejects it. The host migration command creates an authenticated age archive that restores. A forged plain zip with recomputed checksums never reaches an in-app restore run. |
| B5 | medium | Knowing what is where and its value | The generated-key warning fails open: if mount-source comparison is unavailable or ambiguous, it says nothing. An operator can interpret no warning as a safe backup boundary even when the key is co-located with, or exposed through the same storage administration boundary as, the archives. | The current generic rule says a generated state-volume key beside BACKUP_DIR is unsafe, but says nothing when it cannot determine mount sources (docs/specs/SPEC_0300.md:179). The cited document-mount helper only identifies mount points, not mount sources (backend/app/services/documents.py:47-59); it cannot implement the stated comparison without new parsing. | Keep startup non-blocking, but make generated-key safety three-state: verified separate, verified shared, or not verified. Show an explicit persistent warning for both shared and not-verified states, recommending BACKUP_KEY_FILE; never present silence as a positive safety result. Define Docker-secret file readability for the unprivileged cabinet user and forbid the entrypoint from chowning or rotating a secret mount. | Unit-test bind, named-volume, NFS-like, and unreadable-mountinfo fixtures. Shared and unknown produce different warnings, separate does not; a secret readable by cabinet starts, an unreadable one fails before any backup is written, and no secret mount is modified. |
| B6 | low | Control of the collection record; availability | The updated design correctly puts the canonical manifest under the MAC, but its listed tests only name a known SHA256SUMS value and tampered SHA256SUMS. A regression to the previous MAC input would let a share writer wrap an unchanged, valid member set with a changed manifest and original MAC after encrypting to the public recipient. At minimum this can falsify restore metadata or make restore accept an attacker-selected compatible revision. | The MAC rule requires canonical JSON for the manifest plus SHA256SUMS (docs/specs/SPEC_0300.md:169), but the test list names no altered-manifest case (docs/specs/SPEC_0300.md:183). | Add a required conformance test for the exact byte sequence: canonical manifest with mac omitted, followed by SHA256SUMS. The verifier must reject a changed manifest with the original MAC even when every member and SHA256SUMS line is unchanged. | Build a valid archive, alter only a manifest field covered by canonical JSON, preserve SHA256SUMS and mac, re-encrypt it to the public recipient, and assert both in-app inspect and restore.sh refuse it. |

## Consistency problems

- The active behavior revokes every token (docs/specs/SPEC_0300.md:279, docs/specs/SPEC_0300.md:289), but the credential test list still says password change revokes read and write and keeps metrics (docs/specs/SPEC_0300.md:352). Update the test rule before implementation.
- The walkthrough requires BACKUP_KEY_FILE for a lost-machine restore (docs/specs/SPEC_0300-how-it-works.md:177), but the contract's Settings table omits that variable (docs/specs/SPEC_0300.md:409-418). It appears later only as a compose input (docs/specs/SPEC_0300.md:450). Add its precedence, accepted identity-file format, readability rule, and rotation behavior to the Settings table.
- The contract says encrypted inspection decrypts into .restore-staging (docs/specs/SPEC_0300.md:177) and the security document calls that BACKUP_DIR/.restore-staging (docs/security.md:381-385), while both documents promise a backup-share reader learns nothing (docs/specs/SPEC_0300-how-it-works.md:237-262, docs/security.md:341-352). This is the B1 contradiction.
- The historical Phase 5.6 text still presents GET /api/backup.zip as a plaintext zip and says restore.sh validates only SHA256SUMS (docs/roadmap.md:511-557), whereas P8 says every archive is encrypted (docs/roadmap.md:986-996). Mark the historical behavior as superseded by v0.30.0 or update the operational description.
- The contract says the backend believes no forwarded header unless an operator says so (docs/specs/SPEC_0300.md:407), but also removes every proxy-trust setting (docs/specs/SPEC_0300.md:420) and requires --no-proxy-headers (docs/specs/SPEC_0300.md:437). The first sentence should say it never trusts proxy headers in A1.

## Missing or excess

- **v0.30.0, required:** B1 private staging, B2 rotation selection, B3 rollback detection, B4 host-only legacy migration, and B6 manifest-coverage conformance test. These protect or prove the backup boundary the new feature is intended to create.
- **v0.30.0, small cost:** Partially resolved in 25387bc. Section 7 now explicitly recommends a forward-auth or SSO gateway until v0.31.0, requires pass-through of cookies and fetch metadata, and expands its identity-header blank list (docs/specs/SPEC_0300.md:429, docs/specs/SPEC_0300.md:476-484). Retain a deployment verification checklist for the configured gateway: public origin, cookie and fetch-metadata pass-through, photo requests, recent-password confirmation, and an internal metrics-token client. The explicit blanking is sufficient defense in depth because A1 never reads proxy identity headers; an exhaustive list is neither possible nor needed for correctness.
- **v0.31.0:** local passkeys or provider MFA remain the right next security step. The recommended gateway can supply MFA before then, while Cabinet continues to work directly and does not trust gateway identity in A1.
- **No cut recommended:** the extra MAC is not overbuilt. age protects an archive made to the Cabinet recipient, but the recipient is public; the MAC is what prevents a share writer from encrypting a new, attacker-made zip to that public recipient.

## Not verified

- No v0.30.0 encryption, CLI, proxy, or gateway code exists. Findings are against the contract and the current pre-auth implementation, not executed new behavior.
- I did not run the real age binary, Docker secret mount, PostgreSQL restore, nginx auth_request, or any third-party gateway. The age format assessment used the primary [age v1 specification](https://age-encryption.org/v1), checked directly; it specifies authenticated, non-malleable file payloads and an X25519 identity as 32 random bytes encoded with Bech32.
- I did not inspect the live Swarm, backup share, Docker API, .env files, or live Cabinet instance. In particular, the real mount topology and a gateway's pass-through behavior require the deployment-level checks above.
